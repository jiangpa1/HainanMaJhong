## 三、最可能的机制

**无 swap 的严重内存压力 → 用户态进程集体无法推进。** 11:49–11:50 的 40 秒里可用内存从 357 MiB 掉到 84 MiB，此后：
- 进程申请内存/回收页时长时间阻塞在内核路径（direct reclaim），**表现为"卡住"而不是"被杀"**——所以没有 OOM 记录，但 systemd 的 watchdog（journald 3 分钟、snapd 5 分钟）接连超时；
- `systemd-logind` 无法完成会话操作 → sshd 永远发不出 banner；
- 应用的 JVM 也停止响应（actuator 不再被采集到）；
- 一旦进入这种状态，**没有外力（硬重置）无法自行恢复**。

## 四、诱因（按责任排序）

1. **在无 swap 的 1.6 GB / 2 vCPU 实例上启用 JFR `settings=profile`**。JFR 默认仓库在**内存**中且不设上限，叠加"320 并发登录"这种高分配场景，会同时抬升堆外内存与采样线程 CPU。这是本次的直接诱因，也是操作错误（此前已明确不应对本机用 profile 级录制）。
2. **紧接着执行 680 MB 的日志轮转**。`copytruncate` 产生 680 MB 脏页需持续回写；同时被清空的 `game.log` 仍被应用以旧偏移写入（稀疏文件），增加了 I/O 与页缓存压力。
3. **本机没有 swap，也没有对 JVM/整机的内存水位保护**。内存压力没有泄压阀，也没有"提前重启应用"的护栏。

## 五、改正措施

| 优先级 | 措施 | 状态 |
|---|---|---|
| P0 | **不再在本机使用 JFR `settings=profile`**；如需 JFR，只用 `settings=default`、`duration=60s`、`-XX:FlightRecorderOptions=repositorysize=32m,disk=true`，且仅在 256 人档、带内存护栏下 | 本文生效 |
| P0 | **加 swap**（2 GB swapfile 或 zram）：把"整机卡死"降级为"变慢"，是性价比最高的一条 | 待操作者批准 |
| P1 | **主机侧内存护栏**：systemd timer 每 30 秒检查 `MemAvailable`，连续低于 150 MiB 就重启应用（或至少告警），避免再次拖垮全机 | 待批准 |
| P1 | **日志轮转改为小块多次**（64–128 MB）并检查 logback 级别：713 MB / 一天半主要是空闲期的量，偏大 | 待批准 |
| P2 | 给 JVM 明确 `-Xmx`/`MaxRAMPercentage`，长期可选加 cgroup 内存上限，让内核"杀进程"而不是"卡全机" | 待批准 |
| P2 | 剖析改用低开销手段：`jcmd Thread.print` ×3、`/proc/<pid>/task/*/stat` 每线程 CPU、`jcmd GC.class_histogram`、应用自带 Micrometer 指标 | 已定方案 |
