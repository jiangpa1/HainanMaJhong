## 四、三个问题（按严重度）

### P0 阻断：delta 模式收尾卡死（必须修）

**现象**：`freezeAfterRound=true` 后，harness 等每个房间再结算一局（收到 `coins`）即冻结；delta 轮 **64/64 房间在 120 秒内都没有收到这次 `coins`**（full 轮 23 秒全部完成）。窗口内的 300 秒**牌局本身是健康的**（1,200 局结算、`pendingDiscardDeliveries=0`、客户端 0 失败、`coins` 4,800 = 1,200×4 家齐全）。

**机制（初版判断已撤回，见文首更正声明）**：初版把根因归为"事件合并把 `coins` 挂起"，**核对被测包源码后不成立**——`coins` 是直接发送、不参与合并。因此 **P0 的真实触发机制尚未定位**，需要以下证据继续排查：

1. **收尾时刻的逐房间消息时间线**（新版工具已加 `lastSeq`/`pushProtocol`/未匹配广播率）：确认失败房间在 drain 期间**是否收到任何 `coins`/`hand_start`**，以及序号是否连续；
2. **服务端侧同时刻的行为**：drain 期间该房间是否还在推进（`mahjong_engine_timer_pending`、房间状态）、是否有 `resendPending` 造成的请求重发/超时重置；
3. **是否与 `resync` 频率耦合**：被测包 `syncSeats` 每 0.5–0.7 秒对每个 delta 客户端触发一次，并**每次都调用 `member.human.resendPending()`**——若 `resendPending` 重设了待决请求的超时，卡住的一手将永远等不到服务端超时兜底。

**建议的排查顺序**：先用 **1 桌 60 秒 delta** 复现（期望同样卡在 drain），配合新版工具诊断 + 服务端日志（`应答命中`/`重发待决请求失败`/`onIdle` 触发时间）定位；再验证修复。

**复现与验证**：先用 **1 桌 60 秒 delta** 复现（期望：drain 也卡住）；修复后要求 delta 的 `roundDrainSeconds` 与 full 同量级（约 10–25 s）、`pass=True`。

### P1 收益被吃掉：周期快照过密（必须调）

`syncSeats()`（`:787`）的触发条件是 `force || actionsSinceSnapshot >= 10 || 5 秒未发 || resync`。实测每秒约 15 个动作/桌，**"每 10 个动作"≈ 每 0.5–0.7 秒一次**，远密于设计的"每 5 秒"，于是：
- `board` 发送 256 → **63,612 次**、字节 56 KB → **31.5 MB**（占 delta 总字节 26%）；
- `hand` 也被快照额外推了一份（199,280 次）；
- 结果：**发送 −38% 但字节只 −12.6%**，与设计预期（−50% / −52%）差距极大。

**建议**：
1. 提高动作阈值（如 100+）或**直接去掉动作触发**，只保留 5 秒定时 + `hand_start`/重连/`resync` 的强制快照；
2. 可选：`board` 快照做**差量或分片**（例如只补 discards 的尾部），或对同一客户端的快照做最小间隔（如 ≥3 秒）。

参考量级：若快照降到每 5 秒一次，`board` 约 256×4×12 = 12,288 次/300 秒（约为当前的 1/5），字节相应回落。

### P2 更正：`seq` 已实现，缺口检查此前缺位

**初版结论"`seq` 未实现"错误**，已撤回：被测包 `GamePushServiceImpl:178-180` 写入 `GamePushProtocol.SEQUENCE`、`MultiPlayerRoomServiceImpl:193` 消费客户端回传的 `seq`。

**但现象仍需解释**：delta 轮未匹配广播 796 vs full 104（0.32% vs 0.08%）。差异可能来自"合并/延迟发送导致的帧顺序或丢失"，也可能是收尾异常流程的副产物——**旧版压测工具不含 `seq` 跳号检查**，因此无法判定。新版工具已补 `pushProtocol` 协商校验、`lastSeq` 跳号检查与 `unmatchedBroadcastRate`（默认门槛 0.1%）——**这正是定位该现象所需的证据**。

**建议**：新包重测时把 `unmatchedBroadcastRate` 作为回归门槛（要求 ≤0.1%，即回到 full 量级），并记录每次跳号发生在何种消息之后。

### 5.3 结论与仍存在的差距

1. **P0 已解决**：delta 模式收尾正常（1 桌、4 桌、256 人三档均通过），未匹配广播率低于门槛。

### 9.2 CPU 收益远低于预期（重要）

- 有对照意义的两轮：**delta 系统 CPU 0.57 / 进程 0.34** vs **full 0.61 / 0.36**（full 第二轮复现 0.61 / 0.36）→ **实际只降约 0.02–0.04 个核**，而设计预期是 **−0.08 个核**。
- **推论（需更新对瓶颈的认识）**：发送次数减少 46% 只换来 ~0.03 个核，说明**发送路径的边际 CPU 成本远低于先前从 `mahjong_ws_send_seconds_sum` 推得的估计**（那个累计耗时含阻塞在 socket 写上的等待，不是 CPU）。**剩余 CPU 的大头不在"发多少条消息"，而在请求处理 / JSON 构造 / 引擎本身**——后续优化应针对分配与 JSON 构造，而不是继续削消息条数。
- 抵消项：周期快照本身要构造 `board`/`hand`/`counts`（每 5 秒 × 80 房 × 4 座 ≈ 64 次/秒的快照构造 + `serializeMeld`），50 ms 兜底线程还要轮询 80+ 个听众（约 1,600 次/秒），这部分吃掉了相当一部分节省。

### 9.3 P0 缺陷未完全修好：间歇性复现

- 320 档 delta **2 轮中 1 轮（g3）复现**收尾卡死：**0/80 房间冻结、drain 120.1 s**；full 两轮均 21–22 s 正常。
- 失败轮特征与第一轮一致：**80/80 房间结算数均匀（17–18 局）**、客户端 0 失败、0 在途弃牌——**窗口内牌局完全正常，只在收尾时全体停止推进**。
- **并发出现的第二信号**：失败轮未匹配广播率 **0.327%**（1,020/311,784）**超过 0.1% 门槛**；通过轮为 0.045–0.053%。两者很可能同源：**推送延迟/丢弃**同时造成"客户端丢帧"与"某关键帧缺失导致停止推进"。
- 服务端日志：卡死窗口内 **`推送兜底发送失败=0`、`重发待决请求失败=0`、`ERROR=0`**（仅 2 条 `发送消息失败`、82 条 WARN 多为清理期 400）——**没有异常线索**。

### 9.4 下一步（定位间歇缺陷的具体做法）

1. **在卡死窗口内抓线程转储**：房间在 drain 期存活 120 秒，是最佳取证时机。计划：跑 delta 320/300，在 drain 开始后 **+10 s / +40 s / +90 s** 各抓一次 `jcmd Thread.print`（含锁信息）与 `top -H`，看是否有 **BLOCKED** 线程、引擎线程与 `mahjong-push-flush` 是否互相等待。
2. **判断"flusher 卡住还是引擎卡住"**：卡死窗口内采样 `mahjong_ws_resync_total{reason="periodic"}`——若周期快照仍在增长说明 flusher 活着、是引擎线程被阻塞；若也停住则是 flusher/全局锁问题。
3. **复现成本**：320 档 delta 每次约 6 分钟，当前复现率约 1/2；建议连续跑 4 次，只要复现 1 次即可取证。
4. **产品决策**：Phase 1 目前收益是**带宽 −36%（发送 −46%）**、**CPU 仅 −0.02~0.04 核**，代价是**间歇性收尾缺陷 + 复杂度**。若目标只是省带宽，可保留并修缺陷；若目标是提容量，**应转向请求处理 / JSON 分配侧**。

### 10.2 CPU 判定：Phase 1 在 320 档没有可分辨收益

把今天所有**有效**的 320 人轮放在一起（排除收尾失败与 CPU 保护轮）：

| 模式 | 各轮 CPU 均值 | 轮数 | 平均 |

| delta | 0.57（g1）、0.60（h1）、0.66（h2）、0.65（h3）、0.61（h4）、0.59（k3）、0.64（k5） | 7 | **0.617** |

→ **差异 0.004 个核，完全在噪声内。结合 256 档的 −0.02 核，可判定：Phase 1（发送 −46%、字节 −36%）带来的 CPU 收益 ≈ 0。**
这与"发送路径的边际 CPU 成本极低"一致：**瓶颈不在消息条数**，而是请求处理 / JSON 构造 / 引擎本身的 CPU 与分配。

### 10.3 另一项更重要的运营发现：320 档余量比预期薄

- k 系列 **6 轮里 3 轮被 CPU 保护停止**（k1/k4 在登录期、k6 跑到 294 秒）；k6 的 CPU 均值 **0.77**、峰值 1.00、内存最低 354 MiB。
- 叠加此前 p9 系列（重启后 4 次尝试全部在登录期被停）与 g3 的收尾失败：**这台 2 vCPU 机器在 320 人档是"临界可持续"**——登录风暴（256 个并发登录）本身就能短时冲上 0.9+，连续多轮后（堆/线程/元空间/mysqld 状态累积）余量进一步变薄。
- 这不否定 320 作为上限（今天多轮通过），但说明：**换挡前必须重启应用**（恢复余量），且**任何"档位提升"的结论都要在 fresh 进程 + 充分预热下取得**。

### 10.4 Phase 1 总体判定

| 维度 | 结论 |
|---|---|
| 功能开关 | ✅ 生效（`turn` 归零、`counts` −96%） |
| 流量 | ✅ 发送 −46%、字节 −36%（256 与 320 两档一致） |
| **CPU / 容量** | ❌ **无可分辨收益（≈0）**，对容量边界没有帮助 |
| 正确性 | ⚠️ 收尾卡死**间歇复现**（320 档 7 次 delta 中 1 次；256 档 1 次），8 次取证尝试未抓到现场；失败轮未匹配广播率异常（0.32–0.33% vs 通过轮 0.045–0.06%） |
| 复杂度 | ⚠️ 新增兜底线程、周期快照（≈64 次/秒快照构造）、会话属性与协议协商 |

**建议**：
1. **Phase 1 保持默认 `full`（现状）**，不要急着把 `PUSH_DEFAULT` 翻成 `delta`——它的价值是省带宽（若带宽不是约束，收益有限），却带来间歇性收尾缺陷。
2. **若继续投入**：优先修收尾缺陷并抓到现场（触发器 v2 已就位，随今后的 320 长测一起待命；复现率约 1/7–1/8，建议在 3×30 分钟长测中附带取证）。
3. **容量方向应转向**：按 10.2 的结论，下一步应测**请求处理 / JSON 构造 / 引擎**的 CPU 与分配（`GC.class_histogram` 前后差 + 线程组 CPU + 针对性计数），而不是继续削消息条数。
