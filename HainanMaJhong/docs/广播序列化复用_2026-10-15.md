# 优化项 1：公共广播序列化复用（2026-10-15 实施与对照）

对应《逐项优化与线上容量对比_2026-10-14》第二批第 1 项。**已上线并完成对照复测。**

## 一、改了什么

| 文件 | 改动 |
|---|---|
| `service/impl/GamePushServiceImpl.java` | 新增私有内部类 `Encoded`（JSON 文本 + UTF-8 字节数）与两个私有方法：`encodeOrLog(msg)`（序列化一次并记录成本）、`sendEncoded(session, payload)`（发送已编码载荷，仍对 session 加锁）。`broadcastGame` / `broadcastGameMasked` / `sendRoomInfo` 改为**惰性编码一次、多连接复用**；`sendJson`（单收件人）保持原语义。 |
| `monitoring/CapacityMetrics.java` | 新增 `serialized(nanos, size)` → 指标 `mahjong.ws.serialize`（Timer）与 `mahjong.ws.serialize.size`（DistributionSummary）。 |

保留的不变量：`metrics.delivery()` 序号仍在编码前注入（四家看到同一 `_monitorSeq`）；`synchronized (session)` 与 `isOpen()` 复检不变（WebSocket 发送非线程安全）；发送顺序仍按成员遍历顺序；**私有内容隔离不变**——`broadcastGameMasked` 的 owner 用 `full`、其余人用 `masked`，两种内容各只编码一次，绝不互相复用。

**指标语义变化（需注意）**：改造前 `mahjong.ws.send` 含序列化时间；现在它只含发送时间，序列化时间单独记在 `mahjong.ws.serialize`。两者相加才等于改造前的 `mahjong.ws.send`。

**打包踩坑（记录）**：用"补丁式编译"（`javac` 对现存 jar 的 `BOOT-INF/lib` 编译 + `jar uf`）时，新增内部类会生成独立 class 文件 `GamePushServiceImpl$Encoded.class`，第一次只替换了顶层类 → 启动时报 `NoClassDefFoundError: ...$Encoded`，**自动回滚生效**。第二次把全部编译产物入包并逐字节校验 SHA 后启动成功。**结论：补丁式打包必须处理内部类；正式发布仍建议用 Maven 完整构建。**

## 二、计数证据：序列化次数确实降下来了

同一次 16 桌 60 秒冒烟（`b1-smoke-16tables`）与 320 人 300 秒轮（`b2-after-320`）的窗口增量：

| 指标 | 16 桌 60 秒 | 320 人 300 秒窗口 |
|---|---:|---:|
| WS 发送（成功） | 89,145 | 1,940,910 |
| **JSON 序列化次数** | **31,780** | **687,643** |
| **发送 : 序列化** | **2.81** | **2.82** |
| 序列化累计 CPU | 0.341 s | 5.11 s |
| 发送累计耗时（不含序列化） | 2.876 s | 65.55 s |

改造前该比例必然是 **1.00**（每次发送都从 Map 重新序列化）。因此**序列化次数减少约 64.5%**；按改造后 5.11 s/380 s 反推，改造前约为 14.4 s → **节省约 9.3 s 的 CPU / 380 s ≈ 0.024 个核（≈ 全机 1.2%、JVM 自身约 3%）**。

## 三、A/B 对照（320 人 300 秒，改造前 a3 vs 改造后 b2）

| 指标 | 改造前 `a3-attrib-320` | **改造后 `b2-after-320`** |
|---|---:|---:|
| HTTP 请求 / 失败 | 60,001 / 0 | 60,000 / 0 |
| list-v2 P95 | 43.3 ms | **42.9 ms** |
| rounds-v2 P95 | 45.8 ms | **44.1 ms** |
| rounds-v2 P99 / max | 72.3 / 436.7 ms | **60.9 / 225.1 ms** |
| pending P95 | 36.5 ms | **34.2 ms** |
| 广播 P95（最慢桌） | 31.2 ms | **29.6 ms** |
| 客户端在途峰值 | 62 | **20** |
| 分配速率 | 138.1 MB/s | **132.0 MB/s（−4.4%）** |
| minor GC / 暂停合计 | 1,124 / 7.64 s | 1,109 / 8.07 s |
| CPU 均值 / 峰值 | 0.61 / 0.92 | 0.63 / 0.94（噪声内） |
| 广播确认延迟均值（end / hand_start / coins） | 26.6 / 23.5 / 23.6 ms | **24.1 / 21.7 / 21.9 ms** |
| 业务正确性 | 80/80 清理、0 记录错、pass | **80/80 清理、0 记录错、pass** |

**结论**：
1. **改动正确、无回归**：交付验收（P2 口径）、广播送达确认、结算局数（1,503 → 1,504）、清理审计（80/80 房间、`recordErrors=0`、`listErrors=0`）全部正常；`unmatchedBc` 148 → 160 与改造前同量级。
2. **收益符合设计但量级有限**：序列化次数 −64.5%、分配 −4.4%、P99/max 与在途峰值改善；**但 CPU 均值仍是 0.63（改造前 0.61），节省的 0.024 个核被运行间波动（±0.02）淹没。**
3. **这一项不足以改变容量边界**：400 人失败时 CPU 峰值 0.96 且持续 20 秒以上，需要的是"数量级"级别的削减，而本项只解决了一条路径上约 10% 的 WS 处理时间（序列化在 WS 路径中的占比：5.11 s / (5.11+65.55) s ≈ 7.2%）。

## 五、下一步建议

1. **保留本改动**（严格改进，风险低）。若要继续，第二批第 2 项（共享定时器）应当**先测量再改**：本机每条房间线程有一个 `mahjong-timer` 单线程 `ScheduledThreadPool`（80 房 = 80 个池），但线程组采样显示 `room_engine`/`pool` 桶占 JVM CPU ≈0%，**预计收益同样有限**——建议先用线程组采样确认 `mahjong-timer` 的实际 CPU，再决定是否改造。
2. 数据指向的更大目标（按证据排序）：
   - **WS 输出量本身**：栈采样中 `socket_io` 占 47.8%（`FileDispatcherImpl.write0/writev0`），发送耗时 65.55 s / 380 s ≈ 0.17 个核；减少"每人一份、每帧一份"的发送次数或字节量（例如合并帧、按需推送）比优化序列化更有量级空间。
   - **`room-bind-<房间码>` 每房一条裸线程**（占 JVM CPU ≈25%）：这是本轮新发现，且《逐项优化》原文未覆盖。
   - 每房 `mahjong-timer` 池（待测量）。
3. 若要精确定位"广播序列化 / 快照 / 监控 / 查询"各自占比，仍需真 CPU 剖析（async-profiler 或受限的 JFR `settings=default`），见 `docs/热点归属_2026-10-15.md` 第六节。
