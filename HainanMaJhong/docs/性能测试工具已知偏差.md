# 压测工具的已知偏差（2026-10-16）

记录 `docs/performance/` 工具链中**已知会误导结论**的测量行为，以及各自的修法。凡涉及结论的地方都应先看这里。

## 一、未匹配广播率（`unmatchedBroadcasts` / `unmatchedBroadcastRate`）—— 记账伪影

### 现象与判定

它看起来像"服务端丢了帧"，实际是**工具内部跨连接记账的时序错位**：

- 同一房间 4 条连接**共享** `pendingDiscards` 表，键为 `${hand}:${ordinal}`；
- 而 `ordinal` 是**每条连接各自**的计数器（`hand_start` 清零）；
- 某家出牌时按"我当前的 ordinal+1"登记，收到广播时按"我当前的 ordinal"查表；**一旦四条连接的 ordinal 错开**（各自 socket 时序不同），就会查不到 → 计一次 `unmatched`，**而帧其实收到了**；
- 一个条目要被删除需四条连接各自写入一次自己的 client id，因此该计数天然依赖"四条连接同步"。

### 反证（为什么它是伪影而不是丢帧）

| 证据 | 数值 |
|---|---|
| 协议序号（服务端每帧盖章、每连接单调） | 448 人档 273 万帧：**跳号 0、重复 0、缺 seq 0**；此后每轮也都是 0 |
| 同档位不同窗口的未匹配率 | 300 秒窗口 **2.344‰ / 2.273‰**；1800 秒窗口 **0.355‰ / 0.365‰** |
| 反推未匹配**绝对条数** | 四种情况都约 **150 条** → **固定启动瞬态**，随窗口变长被稀释；**真丢帧的"率"应大致恒定** |
| 其他自检 | `pendingDiscardDeliveries = 0`、`discard-broadcast-mismatch = 0` |

### 已做的修法（2026-10-16）

1. **判据换成协议序号缺口**：新增配置键 `maxSequenceGaps`（默认 0，含义为"不允许任何缺口/重复/缺帧"），`s.pass` 改用 `s.sequenceIntegrity`；`unmatchedBroadcastAcceptance` 保留但标记 `gating:false` + `note`，仅作信息项。
2. **记账改为不依赖跨连接同步**：出牌登记与收帧查表都改为按 **`(局, 座位, 牌) 的第几次`** 关联（每条连接各自维护 `seenDiscards`/`bookedDiscards` 计数，因广播顺序一致而必然一致）。这样**别的玩家出牌不再扰动本家的键**。
   - 已冒烟验证：`sequenceIntegrity.gaps=0`；**每房广播延迟样本仍在采集**（n=172–283、P95 22.5–23.8 ms），说明 p2 的"四家广播 P95 ≤150 ms"判据未受影响。

### 仍未修的部分

- **历史轮次不改判**：2026-10-16 之前的"未通过"仍按当时的门槛保留（方法论已注明"未匹配广播也不能直接等同丢帧"）。
- 若将来要让该指标重新入判据，应先按上述第 2 条修完，并**只在长窗口（≥10 分钟）**上评估。

## 二、429 重试会把退避时间算进单请求耗时 —— 我方引入的偏差

> 后续实现更新：`measurementVersion=3` 已拆分 `logicalTiming`、`attemptTiming`、`successAttemptTiming`、原始尝试/429 与退避等待；正式读取默认不重试，准备/收尾默认最多重试四次。以下现象描述旧版结果，不能套到新字段。实现与复验入口见[后续实施](运行边界闭环后续实施_2026-10-16.md)。

为了让工具尊重准入保护的 429 语义，`request()` 对**幂等 GET** 增加了按 `Retry-After` 的退避重试（上限 `TEST_429_RETRIES`，默认 4 次、带 0–200 ms 抖动；写请求不重试）。

**副作用**：`res.ms` 覆盖**整个重试序列**，因此其中的 `Retry-After` 睡眠被计入 → 工具报告的单请求 P95/P99 会被显著抬高。

实测：512 人 @4 请求/秒/桌 那轮，工具报告 P95 ≈ **9.9 秒**，而同窗口**服务端**记账（`outcome="success"` 的 sum/count）显示已接纳请求平均只有 **337 ms**（基线 21 ms）。

**判读规则**：

- 同时报告成功请求的服务端直方图与客户端成功尝试耗时：服务端过滤器可能漏掉前置排队；旧版即使最终 `status===200`，耗时仍可能含之前的 429 和睡眠，不能仅按最终状态过滤就当成功尝试延迟。
- `http.sent / succeeded / rateLimited / failed / skipped` 是逻辑请求与最终状态口径；`http429Retries` 单列重试，但不能代替所有原始 429。新版本另有 rawAttempts/rawRateLimited。重试还会改变实际请求量，不只改变耗时。
- 平均 337 ms 不能推出 P95 必然超过 500 ms，需实际窗口直方图或逐次成功尝试分位。

## 三、阶段间房间清理开销（约 6–8 分钟 / 80 房）

每个 stage 结束后工具会逐房做收尾核验（连接残留、会话结束、房间解散、战绩与列表一致性、pending 复核）。80 房实测约 **6–8 分钟**，128 房更久。因此：

- 多档阶梯的总时长 ≈ Σ(每档 300 秒) + Σ(每档清理 6–8 分钟) + 登录准备（见下），**不要按"档位 × 5 分钟"估时**；
- 报告里应把清理与压测窗口分开陈述。

## 四、登录准备按 1.1 秒/账号限速（与 `LOGIN_IP_RPS=1` 对齐）

工具默认 `loginIntervalMs=1100`，与线上单 IP 登录额度一致，因此 320 账号约 **6 分钟**、512 账号约 **9.4 分钟**准备时间，且**已认证账号在同一个进程的阶梯里只付一次**。准备阶段不计入正式窗口。

## 五、输出目录复用会秒退

工具要求输出目录**新建或为空**；若目录里残留 `resource-stop.json` / `monitor-done.json`，下一次运行会立即停止（曾导致"业务复跑 0.2 秒完成"的假结果）。每次运行使用新目录。

## 六、`rpsPerTable` 上限 5

配置校验限制 `0 < rpsPerTable ≤ 5`。需要更高读压力时只能提高档位（人数/桌数，`tables ≤ 128`），或临时调整该上限——但那会改变"标准画像"的可比性，需在报告中显式说明。
