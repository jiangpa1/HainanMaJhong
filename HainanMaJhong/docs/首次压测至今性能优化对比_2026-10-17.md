# 从第一次压测到运行边界验证的性能优化对比

整理日期：2026-10-17，北京时间。范围为现存本地报告中的 2026-10-08 至 10-17 证据。本次只整理资料，没有重新发压、部署或修改线上参数。

## 结论

已验证的演进是：从早期单接口探测，发展为真实对局与查询混合压测；从 192 人、5 分钟的早期基线，取得了预热后 320 人、同进程两轮各 30 分钟的完整证据。最直接的优化收益来自战绩 P2 读模型、分页与压缩，随后通过数据库内存调整、入口限额修正和准入保护补充运行余量与过载行为。

这不是单一代码版本的连续 A/B。CPU 保持 2 vCPU，但带宽由 10 升到 20 Mbps，MySQL 内存配置、swap、账号历史、预热、采样及保护门槛均有变化。因此不能把人数或延迟的全部变化归因于代码优化。

## 2. 各项优化到底改善了什么

| 项目 | 前 → 后 | 可成立的收益 | 不应写成 |
|---|---|---|---|
| 首屏分页 | 1,000 局构造样本 860,326→6,319 B | 首屏未压缩业务对象约 **−99.27%** | 总带宽、CPU 或所有查询都减少 99% |
| HTTP gzip | 同轮解码正文 101.42→传输正文 24.16 MiB | 该轮正文约 **−76.2%** | 与分页节省率相乘，推算整个系统收益 |
| P2 数据库路径 | 64 人受控窗口累计 SQL 耗时 14.3→4.1 s | 约 **−71.3%**，直接查询成本证据较强 | CPU 降低 71%，或每个接口均降低 71% |
| P2 前后 192 人延迟 | 失败热轮 P95 684.4→完整轮 32.6 ms | 观察值约 **−95.2%**，同时从中止转为跑满 | 两个完全等长、等历史、等缓存的严格 A/B |
| Hikari 排队 | P2 前 pending 峰 51→后 0 | 测试窗口内排队压力明显缓解 | 所有负载下永不排队；后续超载曾再出现峰 37 |
| MySQL 常驻占用 | RSS 644→354 MiB | 约 **−290 MiB / −45%** | 应用自身堆或全机内存都降低 45% |
| 广播编码复用 | 每发送编码一次→编码/发送约 1/2.82 | 编码约 **−64.5%**，分配速率约 **−4.4%** | CPU 明确降低 64.5%，或 Timer 累计耗时就是 CPU 时间 |
| delta 推送 | 发送约 −46%、字节约 −36% | 降低该模式的推送流量 | CPU 容量提升；默认已切 delta；收尾缺陷完全解决 |
| 生命周期/Outbox | 易发生迟到写、关闭补偿依赖人工→条件写和持久补偿 | 增加正确性、可恢复性 | 未测得的 QPS 提升、覆盖所有崩溃和所有结算故障 |

## 3. 从最早基线到现在，可以怎样比较

| 维度 | 早期证据 | 后续最有代表性的证据 | 解读 |
|---|---|---|---|
| 测试覆盖 | 单个公网战绩列表、5/10 RPS 探测 | 四账号/桌、持续对局、五类查询、广播、账目及收尾 | 测量对象更接近实际系统，但与第一次不再同画像 |
| 混合活跃人数 | 192 人/48 桌，300 秒通过 | 320 人/80 桌，两轮各 1,800 秒通过 | 验证点人数约 **+66.7%**；不是同条件证明的纯代码容量增幅 |
| 混合查询目标速率 | 120 GET/s | 200 GET/s，持续对局 | 同为每桌 2.5 GET/s，总查询目标约 **+66.7%**；其中约 4/5 是战绩、1/5 是 pending |
| 连续单轮时长 | 300 秒 | 1,800 秒，重复两轮 | 每轮时长 **6 倍**；两轮不能冒充一次不中断的 60 分钟实验 |
| 尾延迟 | 10/09 192 人 P95 39.0 ms | 10/16 320 人 P95 43.6/50.8 ms | 更高负载、更长窗口下仍在几十毫秒量级；相对最早混合基线并非延迟下降 |
| 短时更高档位 | 256 人旧轮失败 | 480 人 300 秒零失败通过，512 人窗口零 HTTP 失败但原整轮未过 | 短测覆盖显著扩展，不能直接用作长期运营承诺 |
| 故障处理 | 早期证据较少 | 分类拒绝、降载恢复、告警及双向切包演练，后来加 Outbox 补偿 | 提升运行可控性，不等同于移动吞吐边界 |

因此不采用“第一次 10 RPS，后来 200 RPS，所以性能提升 20 倍”的说法。也不把 10/08 的 1.58 秒与最新 JMeter 23 ms 算作同接口纯优化倍数。

## 4. 最新反证：重试可能抵消削峰

10/17 全局 160/16、同为 320 人和 240 目标 GET/s 的单组对照：

| 指标 | 正式 GET 不重试 | 最多重试 4 次 | 观察 |
|---|---:|---:|---|
| 逻辑读取发送 | 72,001 | 72,001 | 逻辑目标相同 |
| 原始 HTTP 尝试 | 72,001 | 170,745 | **2.37 倍** |
| 原始 429 | 9,616 | 108,026 | 约 **11.2 倍** |
| 最终成功 | 62,385 | 62,719 | 只多 **334** 次，约 **+0.54%** |
| 已采集路由的服务端最大 P95 | 约 22 ms | 约 250 ms | 约 **11.4 倍**；不包含漏采路由 |
| 日志 CPU 均值 | 0.399 | 0.523 | 约 **+31%**，不同轮次仍有环境噪声 |

结论：扩大重试预算没有在这组数据中带来足够的成功增益，反而显著增加请求量、拒绝与延迟。它比继续盲目调小并发或放大连接池更值得优先处理。来源：[10/17 复核](压测复核与JMeter报告_2026-10-17.md)。

## 5. 必须保留的失败和测量限制

1. **10/11 并没有因流量下降就全面变快**：当时公网轻载也有约 0.6–1.4 秒延迟，账号历史在增长；原 baseline 只要求接口/广播 P95 <3 秒，后来 P2 的接口门槛为 P95≤500 ms、P99≤2 秒。不同“通过”不是同一质量标准。
2. **保护策略变更不是代码性能提升**：旧 CPU 策略 >0.9 连续三次采样停止；极限实验用过 >0.97/约 60 秒；现为 >0.95 持续实际 60 秒。可用内存底线也存在普通 100 MiB、极限 80 MiB 的区别。
3. **CPU 0.647 是主机使用率比例**，不是 0.647 个核。Timer 的累计 elapsed time 也不是 CPU 时间。delta 的 0.617/0.613 差异不可直接按“核”表述。
4. **冷启动仍是独立边界**：10/16 重启后首次直接上 320 人，约 70 秒触发持续 CPU 护栏；0 HTTP 失败不能把被中止的轮次算作完整通过。
5. **后续版本不能继承旧包长测**：`44f94228…` 的 320 人两轮长测，不自动覆盖 `1311b555…` 或 10/17 最新 Outbox 包。新版本已有专项证据，但没有因此新增同条件长测结论。
6. **服务端直方图解析存在漏路由**：10/17 复核发现标签值含 `{id}` 时，旧正则提前被 `}` 截断，overview/rounds 未采到。已有列表/pending 达标不代表所有接口达标，原 `pass=false` 也不能全解释成服务端性能失败。
7. **最终清理和按时收尾是不同要求**：收尾等待超时后最后查到清理完成，仍保留超时；Outbox 只补关闭事务提交后的 Redis 清理，不自动解决关闭前的 drain 超时，也不覆盖 MySQL 无法提交。
8. **JMeter 是 HTTP 补充证据**：80 个读取线程轮用 320 个登录账号，只有列表两页/pending，不含 WS 对局、overview/rounds；HTTP 200 尚缺业务断言，不能标成完整对局吞吐验收。

## 6. 现在适合怎样概括项目成果

> 在固定 2 vCPU 的小规格实例上，以真实对局与战绩查询混合画像持续复测，通过分页压缩、P2 查询路径和资源配置优化，将验证范围从 192 人 5 分钟推进到预热后 320 人两轮各 30 分钟。受控实验数据库累计语句耗时下降约 71%，线上 gzip 正文减少约 76%；同时补齐准入、超载恢复、监控及回退证据。更高档位长期容量、当前最新版本的长测及间歇收尾仍需独立验证。

下一步先修测量缺口、区分缺陷失败与性能失败，再固定版本/数据/预热/实际 RPS，比较无重试和有限重试；在预算选定且收尾正常后重复长测。继续提高人数之前，先取得可信、完整、可复现的通过证据。
