# B 计划：量测 CPU 的真实去向（2026-10-15 拟定）

## 一、为什么要做

Phase 1 的实测给出了一个反直觉结论：**发送次数减少 46%、字节减少 36%，CPU 却几乎没有变化**（320 人档 delta 7 轮均值 0.617 vs full 3 轮 0.613）。这否定了"瓶颈在消息条数/序列化"的假设，也把优化方向从"削推送"推向"**请求处理 / JSON 构造 / 引擎本身**"。

当前已知（320 人档，JVM 自身约 0.8 个核）：
- Tomcat 请求线程 ≈65%、`room-bind-*` 房间引擎线程 ≈25%、lettuce ≈8%、GC ≈2%、JIT 热机后 ≈0%（`docs/热点归属_2026-10-15.md`）；
- 分配速率 ≈138 MB/s（256 人档实测），minor GC ≈1,100 次/300 秒；
- 栈采样中 `socket_io` 占栈顶 47.8%，但那条路径的**边际 CPU 已被证明极低**——说明采样到的"阻塞等待"不是 CPU 消耗。

## 二、待验证的三个假设（按可能性排序）

1. **每事件构造临时集合**：广播路径上几乎每个事件都 `new HashMap<>()` + `ArrayList`（`GameEngineServiceImpl` 里 `broadcastGame(room, m)` 的 `m`、`counts` 的 map、`board` 的 discards/melds/flowers 三个 map + 每副露一个 map、`coinView()` 的 LinkedHashMap 等）。按约 5,000 条消息/秒估算，这是分配速率的主要来源之一。
2. **每个观察者重建同一份公共数据**：`board` 在按座位的循环里**逐座重建**（含 `serializeMeld` 逐副露建 map），即使内容与上一位观察者完全相同（暗杠隐藏时只有少数座位不同）。
3. **JSON 构造本身**：Jackson `writeValueAsString` 对深层嵌套 Map/List 的遍历与字符串拼接（按 Phase 1 实测：序列化 5.11 s/380 s ≈ 0.013 核，**占比很小**，故此项优先级最低）。

## 三、量测手段（全部低开销、不需要 JFR）

| 手段 | 回答什么 | 成本 |
|---|---|---|
| `jcmd <pid> GC.class_histogram` 前后差 | **存活对象**按类的增量（哪些类在长、哪些是短命垃圾） | 每次触发一次 full GC 级别遍历，建议只在窗口首尾各一次 |
| 现成的线程组 CPU 采样（`attrib-group4.sh`） | Tomcat / 引擎 / Redis / GC / JIT 各自份额（已有基线） | 纯 `/proc`，≈2% |
| `jvm_gc_memory_allocated_bytes_total` 窗口增量 | 该窗口**总分配字节**与分配速率 | 零成本（已有） |
| `jvm_gc_pause_seconds_{count,sum}` 窗口增量 | GC 次数与暂停总时长（分配压力的后果） | 零成本（已有） |
| 应用自带计时器 | 各路由 `mahjong.http.response` 的 P95/P99（判断哪条请求路径最贵） | 零成本（已有） |
| **定向计数（需一次代码改动）** | 每个事件路径构造的集合数量（如 `broadcastGame` 每事件 1 个 map）→ 用计数 × 单次成本估算 | 低（懒注册 Gauge，同 Phase 1 计数方案） |
| `-XX:+PrintTLAB`（**需带参重启**） | **每线程**的 TLAB 分配统计 → 定位"谁在分配" | 重启 + 日志量中等；不引入采样钩子 |

**明确不做**：JFR `settings=profile`（10-15 事故原因）；如确需 JFR，只允许 `settings=default` + `-XX:FlightRecorderOptions=repositorysize=32m,disk=true` + 限时 60 秒 + 仅 256 档，且需操作者批准。

## 四、执行顺序（建议）

1. **先做零改动的两轮对照**（delta/full 各 300 秒，256 与 320 各一次）：取 `GC.class_histogram` 前后差 + 分配速率 + 线程组 CPU + 路由 P95。目的：确认"分配速率是否随模式/档位变化"，以及**哪些类在窗口内净增长**。
2. **再做一次定向计数改动**（只加计数、不改行为）：在 `broadcastGame` / `board` 构造 / `coinView` / `serializeMeld` 上计数每事件构造的集合数与字节数。目的：把"分配速率 138 MB/s"拆到具体调用点，拿到可优化项的量级。
3. **按量级决定优化**：优先做"每事件不新建集合 + 公共数据只构造一次"这类**无契约风险**的改动（与 Phase 1 不同：它不改协议、不动前端），然后同条件 A/B。
4. 通过后再做 320 人 3×30 分钟验收。

## 五、成功判据

- 能回答"**138 MB/s 的分配里，前三大来源各占多少**"；
- 相应优化后：**分配速率下降 ≥30%**、minor GC 次数与暂停总时长同步下降、**320 人档 CPU 均值下降 ≥0.05 核**（0.61 → ≤0.56），且 P95/P99 不劣化、业务断言全过。

## 六、实测结果（2026-10-15 17:36–18:16，320 人档，261 个 5 秒采样）

新增采样器 `/root/cpu-split.sh`：同时按 **Micrometer 口径**（defA = 1 − idle/total，iowait 记作忙）与**排除 iowait 口径**（defB）计算，并逐进程拆 `java` / `mysqld` / `redis`（取 `/proc/<pid>/stat` 的 utime+stime 增量）。

| 阶段 | n | defA | defB | iowait | java | mysqld | redis |
|---|---:|---:|---:|---:|---:|---:|---:|
| 登录期（rooms=0, java>0.5） | 13 | 0.752 | 0.751 | 0.1% | **1.42**（峰 1.67） | 0.03 | 0.00 |
| **牌局中（rooms≥60）** | 187 | **0.710** | 0.703 | 0.7% | **0.84**（峰 1.10） | **0.33**（峰 0.40） | 0.05 |
| 空闲 | 37 | 0.046 | 0.045 | 0.1% | 0.02 | 0.01 | 0.00 |

### 6.1 三条修正后的认识

1. **iowait 假设证伪**：`defA ≈ defB`、iowait ≤0.7%，说明 `system_cpu_usage` 基本就是真实 CPU 忙——先前"重启后 MySQL 缓冲池冷 → iowait 抬高指标导致保护误判"的猜测**不成立**（MySQL 已调优且工作集小，几乎不落盘）。
2. **登录风暴是纯 Java 的 1.42 核**（峰值 1.67，占 2 vCPU 的 71–84%），持续约 20 秒，`mysqld` 此时只有 0.03 → 320 个账号的 bcrypt 登录本身就把机器推到保护线附近。
3. **MySQL 是重要消费者（0.33 核 ≈ 软件 CPU 的 28%）**，此前一直被忽略。同期 HikariCP：**84,283 次连接获取 / 5 分钟 ≈ 280 次 DB 操作/秒**，平均持有 4.96 ms，零等待、零超时（池不是瓶颈，但调用量极大）。
4. **软件 CPU 构成**（牌局中）：java 0.84 + mysqld 0.33 + redis 0.05 = **1.22 核 / 2 vCPU = 61%**，与系统口径 0.71 一致（余量为 nginx/systemd/采样器本身）。

### 6.2 牌局中 defA 的分布（187 个采样）

| 区间 | 次数 |
|---|---:|
| 0.2–0.5 | 9 |
| 0.5–0.7 | 6 |
| **0.7–0.8** | **167** |
| 0.8–0.9 | 3 |
| >0.9 | **0** |

→ 牌局稳态**紧贴 0.71**，而保护阈值是 0.9；但 m2-r1（17:25）与 n1（17:30）实测出现过连续 0.94/1.00/1.00 的窗口——说明**同一档位在不同时刻可落在 0.71 或 0.85+ 两个区间**，与 JIT/GC/负载相位有关。

### 6.3 据此修正的优化优先级（já 量化）

| 目标 | 量级 | 手段 |
|---|---|---|
| **轮询类读接口** | mysqld 0.33 核中占大头（`/api/v2/records` 34,482 次、`/overview` 17,241 次、`/api/room/pending` 18,070 次 per 5 min） | 服务端短 TTL 缓存 / 合并轮询 / 客户端降频；需先做"关掉轮询 vs 打开轮询"的对照量化 |
| **登录风暴** | java 1.42 核 × ~20 秒 | 登录排队/限流（保护机器）、或对同一账号的并发登录去重；属韧性项，非稳态容量项 |
| **牌局请求处理与 JSON** | java 0.84 核的剩余部分（WS 推送已证明只占很小一块） | 定向计数 + 少建临时集合 |

**下一步建议**：先做 **"轮询开关"对照**（320 人 300 秒：正常轮询 vs 轮询降到 1/5），直接量化轮询在 mysqld 0.33 核与 java 0.84 核里各占多少——这是当前最有可能一次性降 0.1 核以上的动作，且**不改协议、不动前端**。
