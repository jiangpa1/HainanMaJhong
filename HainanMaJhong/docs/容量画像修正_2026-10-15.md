# 容量画像修正（2026-10-15）：320 人"容量墙"主要是测试画像造成的

## 一、起因：一次轮询对照

在追查"320 人档 CPU 恰好压在保护阈值上"时，我先做了 CPU 分解，发现 MySQL 吃 0.33 核（此前从未测量），进而做了**轮询开关对照**：

| 320 人 300 秒 | q1 轮询 2.5 请求/秒/桌 | q2 轮询 0.5 请求/秒/桌 |
|---|---:|---:|
| 结果 | **失败（CPU 保护）** | **通过** |
| 系统 CPU | 0.708 | **0.396** |
| Java | 0.84 | **0.44** |
| MySQL | 0.33 | **0.11** |
| HTTP 请求数 | 46,134 | 12,000 |
| 最慢 P95 | 50.9 ms | **33.0 ms** |
| 结算局数 | 1,178 | **1,503（+28%）** |

**轮询类读接口（5 条 records/pending 路由）占了 320 档约 44% 的 CPU（java 0.40 + mysqld 0.22）。**

## 二、这个轮询量不是生产行为（已核对前端源码）

- `frontend/src` 中**没有任何周期性 HTTP 请求**：`setInterval` 只出现在 `TurnTimer.vue`（本地倒计时）与 `GameTable.vue:190`（本地时钟）；WS 重连、战绩页按需请求（`useRecordTask.js` 是重试退避）之外无轮询。
- 牌局状态完全走 WebSocket 推送，客户端不需要轮询。
- 压测工具自述其负载为 "**Same aggressive game and records load** as the previous test: 2.5 HTTP requests per table per second" —— 这是为压测 **P2 战绩读路径**而设计的**压力档**，不是生产画像。

## 三、真实画像下的容量重测（`rpsPerTable=0.1`，300 秒，full 模式）

| 档位 | 结果 | 停止原因 | 结算 | CPU 均 / 峰 | 内存最低 | HTTP 最慢 P95 | 未匹配广播率 |
|---|---|---|---:|---:|---:|---:|---:|
| 320 人 | ✅ 通过 | — | 1,487 | 0.35 / 0.79 | 508 MiB | 36.6 ms | 0.05% |
| 384 人 | ✅ 通过 | — | 1,825 | 0.40 / 0.79 | 491 MiB | 37.9 ms | 0.07% |
| **400 人** | ✅ **通过** | — | 1,874 | 0.36 / 0.84 | 483 MiB | 36.8 ms | 0.08% |
| 448 人 | ❌ 失败 | `stage-acceptance-failed` | 2,140 | **0.40 / 0.88** | 469 MiB | 44.8 ms | **0.147%** |

448 人失败的具体判据**只有一条**：`unmatchedBroadcastAcceptance.pass=false`（0.147% > 0.1% 门槛）。其余全部通过：
- CPU 从未触发保护（均值 0.40、峰值 0.88）；
- HTTP 3,361 次请求 0 失败、无跳过、各接口 P95 ≤ 44.8 ms、P99 ≤ 140 ms；
- 112 个房间清理全部干净（0 连接残留、会话全部结束、房间全部解散、战绩与列表检查 0 错误）；
- 每个房间 0 客户端失败、0 在途弃牌。

## 四、修正后的结论（替换此前的"320 人是上限"）

1. **此前的"320 人容量墙"主要是测试画像的产物**：把合成的读接口压力（2.5 次/秒/桌）降到 0.1 后，**400 人完全通过**，且 CPU 只用掉 0.36–0.40（2 vCPU 的 18–20%）。
2. **历史上 384/400 的"失败"需要重新解读**：它们都跑在压力画像下（384 在 151 秒、400 在 113 秒被 CPU 保护停）。在真实画像下这两档都轻松通过。
3. **新的绑定约束是"丢帧率"而不是 CPU**：未匹配广播率随并发单调上升（0.05% → 0.07% → 0.08% → 0.147%），448 人时越过 0.1% 门槛。这与之前"delta 模式间歇收尾卡死"属同一族问题——两次收尾失败轮的未匹配率都异常偏高（0.32–0.33%）。
4. **CPU 还远未成为限制**：448 人 CPU 0.40；按线性外推，CPU 可能到 800–1000 人才成为约束（内存 469 MiB@448 会先生效）。

## 五、后续建议（按优先级）

1. **两套画像分开记录与使用**（重要）：
   - **生产画像**（`rpsPerTable` ≈ 0.1 或按真实客户端行为）→ 用于**容量结论**；
   - **读路径压力档**（`rpsPerTable=2.5`）→ 保留为 **P2 战绩接口的极限测试**，不再当作容量依据。
2. **修丢帧（新的第一优先）**：它现在是唯一挡住 448 的判据，且有干净的可测门槛（未匹配率 ≤0.1%）。建议做一次**决定性对照**：把 448 人档跑在 **Phase 1 之前的 jar**（`jar-backup-20261015-134059.jar`，SHA `121d69eb…`）上——若未匹配率回到 0.05–0.08%，说明 Phase 1 的事件合并/延迟发送引入了丢帧，应回退或修好再谈 Phase 2。
3. **顺带确认丢帧的用户可见后果**：客户端靠 `discard` 消息维护牌河（`onDiscard` 追加），0.15% 的丢帧在多局后会表现为**牌河缺张**——建议在前端加"`seq` 缺口检测 + 请求重同步"（设计评审里的 `resync` 机制已具备服务端基础，前端尚未接入）。
4. **读接口缓存仍有价值**（若将来客户端真的开始轮询、或做排行榜类轮询功能）：1–2 秒 TTL 可把这条路径的 CPU 再压一半以上。
5. **不要再把"加 vCPU"当作提升容量的首选**：真实画像下 CPU 不是瓶颈；此前"400 人必须加 CPU"的表述应改为"**在 2.5 次/秒/桌 的读压力画像下未通过**"。

## 六、测量口径备忘

- CPU 分解采样器 `/root/cpu-split.sh`：5 秒粒度，同时给出 Micrometer 口径（`1 − idle/total`）与排除 iowait 口径，并逐进程拆 `java`/`mysqld`/`redis`（`/proc/<pid>/stat` 的 utime+stime 增量）。
- 实测 iowait ≤2.4%，`system_cpu_usage` 基本等于真实 CPU 忙（"iowait 抬高指标"的猜测已证伪）。
- 320 档登录期（320 个账号 bcrypt）**Java 单独 1.42 核（峰值 1.67）持续约 20 秒**，是"重启后首次高并发轮次挂在开头"的直接原因；预热应使用**目标档位本身**。
