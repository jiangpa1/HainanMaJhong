## 指标的实际含义

| 层级 | 已采集 | 测量范围 |
|---|---|---|
| 业务 | 活跃/在线/空闲真人、占座数、房间状态、动作接收率、结算提交率、关闭/结算失败 | 10 秒采样近似值；活跃指 PLAYING、非托管、游戏连接在线。动作收到不等于动作被引擎接受；结算在事务 afterCommit 计数 |
| HTTP | 路由模板请求率、业务/HTTP 错误率、P50/P95/P99、首写计时、正文大小 | code!=200 即使 HTTP=200 也算业务失败；正文大小是 UTF-8、Nginx 压缩前；只监测 /api/ |
| WS | 鉴权握手、房间/游戏连接、断线率、发送等待与耗时、消息大小、四人 ACK | pending 是同步发送及等待 session 锁的调用；不是操作系统 TCP 队列 |
| JVM | 堆/非堆、GC 暂停、线程/阻塞、引擎/定时器线程、定时器队列、进程 CPU/FD | JVM/进程指标由 Actuator 提供；定时器取消任务及时从队列移除 |
| MySQL | Mapper 方法、结算/关闭事务、Hikari 池与连接获取、全局慢查询及行锁累计统计 | 方法耗时包含取连接与映射；事务计时包含提交；全局统计包括其他 DB 客户端 |
| Redis | 快照仓储耗时、写入拒绝/异常、INFO 内存/命中/过期/淘汰 | 写入拒绝与异常分开；INFO 是 Redis 全局统计 |
| 主机 | CPU ticks、MemAvailable、指定网卡流量、TCP 重传、物理磁盘 I/O | Linux /proc 采样；非 Linux 或网卡缺失会显示不可用/缺失，不编造数值 |

HTTP 首写计时是应用第一次写出，不是客户端 TTFB；完整处理耗时也不包含公网下载时间。实际客户端 TTFB/完整接收可使用现有受控请求脚本记录，不用服务器计时替代。

关键广播 `hand_start/coins/end/match` 在四名真人游戏连接都在线时带 `_monitorSeq`；新版客户端在消息处理后回 ACK。只有四人全部确认才计入分位数。此指标从广播到最后 ACK，是送达延迟的往返上界，包含回程和客户端调度，不代表画面渲染完成。旧客户端不确认，因此需要把 ACK 超时率一起看。最多跟踪 2048 个广播，15 秒后过期，避免监控缓存无限增长。

慢 SQL 的完整日志与 EXPLAIN、MySQL 活跃事务明细、底层 WS 发送队列、云平台限速/丢弃仍需按需接入或排查；当前面板明确显示此限制，不把缺失数据当 0。这里不增加定时扫描玩家/事务明细，也不自动修改线上慢查询日志设置。

## 部署与访问

**监控已迁到云服务器（2026-10-16）后，本机只需要看板**：双击 `ops/monitoring/start-dashboard.cmd`（或 `start-dashboard.ps1`）。它会①把 `9090/9093/9091` 隧道到云端（缺哪个补哪个）②只启动 Grafana ③校验 `9090` 后面确实是云端 Prometheus（规则文件须以 `/etc/prometheus/` 开头）④打印各抓取目标健康度⑤打开 `http://127.0.0.1:3000/d/hainan-capacity`。日志按启动时间戳写入 `F:\MahjongMonitoring\launcher-logs`；支持 `-NoBrowser` 与 `-ValidateOnly`。

> ⚠️ **不要再对本机用 `start-monitoring.ps1`**：它会启动**本机** Prometheus 与 Alertmanager，会抢占 9090 端口、并让同一条告警**发两封邮件**。该脚本保留给历史/离线场景（云端不可用时临时接管）。

Windows 运维电脑已安装 Prometheus/Grafana，且数据源和面板已导入后，可直接双击 `ops/monitoring/start-monitoring.cmd`。

启动器默认使用 `F:\MahjongMonitoring\prometheus`、`F:\MahjongMonitoring\grafana` 和当前 Windows 用户的 `.ssh\mahjong_ops`。它检查 Windows AMD64 程序和配置文件，依次建立 SSH 隧道、启动 Prometheus 与 Grafana，健康检查通过后在浏览器打开 `http://127.0.0.1:3000/d/hainan-capacity`。三个服务在后台运行，成功后启动窗口可以关闭；重复执行会复用已运行的服务，不重复启动或停止其他占用端口的程序。

脚本启动日志在 `F:\MahjongMonitoring\launcher-logs`。电脑重启后再执行一次即可。首次数据源配置和面板导入仍需完成，启动器不会修改 Grafana 登录账号或自动导入面板。

也可以从 PowerShell 执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "F:\HainanMaJhong2\HainanMaJhong\ops\monitoring\start-monitoring.ps1"
```

安装目录变化时，可传入 `-MonitoringRoot "新的根目录"`；只检查文件和架构、不启动服务时使用 `-ValidateOnly`。启动器使用 `grafana.exe server`，也兼容老版本的 `grafana-server.exe`。

按项目现有流程部署新 JAR 后，可在服务器检查：

```bash
curl -fsS http://127.0.0.1:9091/actuator/prometheus | head
ss -lnt | grep 9091
```

监听地址应为 127.0.0.1。不要把 9091 加到 Nginx 公网代理。`MANAGEMENT_PORT` 可换端口；`CAPACITY_NETWORK_INTERFACE` 默认 eth0，部署前用 `ip -br link` 核对。生产默认启用 Redis/MySQL INFO/STATUS 采样，可通过 `CAPACITY_EXTERNAL_PROBES_ENABLED=false` 关闭；MySQL 池无空闲连接时跳过探测，面板 probe.up=0。探测失败不清空上次值，因此应结合探测状态与采样滞后判断。

服务器内存有限，Prometheus/Grafana 可以运行在运维电脑或监控机上。通过 SSH 隧道让本地 Prometheus 访问管理端口：

```powershell
ssh -i "$env:USERPROFILE\.ssh\mahjong_ops" -N -L 9091:127.0.0.1:9091 root@39.107.247.119
```

把三个监控配置文件放到监控机同一目录，启动已安装的 Prometheus（根据实际资源设置数据目录和保留期）：

```bash
promtool check config prometheus.yml
promtool check rules capacity-alerts.yml
prometheus --config.file=prometheus.yml --web.listen-address=127.0.0.1:9090 --storage.tsdb.retention.time=7d
```

Grafana 添加 Prometheus 数据源并指向 `http://127.0.0.1:9090`，在 Dashboard Import 导入 `capacity-dashboard.json`，选择数据源即可。若 Grafana 在容器中，请把数据源地址改为该容器能访问到的 Prometheus 地址。告警规则已提供，但发送通知还需要现有 Alertmanager 接收端配置；本次没有新建通知渠道。

出网带宽 2026-10-14 由 10Mbps 升到 **20Mbps**，仓库里已同步：告警阈值 `capacity-alerts.yml` 为 **15000000 bit/s**（20Mbps 的 75%），面板变量 `outbound_bps=20000000`（`capacity-dashboard.json`、`generate-dashboard.py`）。带宽每次变化都要同时改这两处。四人 ACK 不直接套用单向送达 150ms 的阈值。

### 改了规则/面板后怎么让它生效

Prometheus 读的是**运维机上的副本**，改仓库文件不会自动生效，必须"部署 + 重读"两步：

```powershell
# 1) 部署规则文件
Copy-Item <repo>\HainanMaJhong\ops\monitoring\capacity-alerts.yml F:\MahjongMonitoring\prometheus\ -Force
# 2) 先校验语法
& F:\MahjongMonitoring\prometheus\promtool.exe check rules F:\MahjongMonitoring\prometheus\capacity-alerts.yml
# 3) 热加载（需要 Prometheus 以 --web.enable-lifecycle 启动；Windows 无 SIGHUP）
curl.exe -X POST http://127.0.0.1:9090/-/reload
# 4) 验证：规则表达式里应能看到新阈值
curl.exe -s http://127.0.0.1:9090/api/v1/rules | findstr 15000000
```

- 改主机上的 `prometheus.yml`（抓取目标等）也能这样热加载；但改**启动参数**（`--web.enable-lifecycle`、数据目录、保留期）必须重启进程。`ops/monitoring/start-monitoring.ps1` 目前启动 Prometheus 时**没有** `--web.enable-lifecycle`，用该脚本重启后热加载会失效。
- reload 是原子的：新规则解析失败会保留旧配置并在日志报错，不会让 Prometheus 退出。
- **Grafana 面板**：`outbound_bps` 是导入后的 dashboard 变量，存在 Grafana 自己的库里，改仓库 JSON 不会自动更新。要么在 Grafana 里改（Dashboard → Settings → Variables → `outbound_bps` → 20000000 → Save），要么把 `capacity-dashboard.json` 重新 Import。
- **Prometheus 侧的告警规则不在 Grafana 的 Alert rules 页**（那里默认只列 Grafana 托管的规则）；直接看 `http://127.0.0.1:9090/rules` 与 `/alerts`，或在 Alert rules 页切换到数据源托管（Data source managed）过滤。
