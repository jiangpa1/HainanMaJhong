## 本次发现的测量缺口

`docs/performance/success-histogram.mjs` 用 `([^}]+)` 匹配 Prometheus 标签块；标签值中的 `/api/v2/records/{id}/overview`、`/rounds` 带 `}`，因此匹配失败。本地用原正则构造三条样例复核：列表能匹配，两条详情路由均失败。

这些额度轮的 `acceptedServerLatency.routes` 实际只有 `/api/v2/records` 和 `/api/room/pending` 两项；而超载判据要求至少三项。因此 `acceptedLatencyAcceptance.pass=false` 含有明确的采集缺口，不能仅凭此断言服务端延迟超标，也不能把已有两项达标解释为全部路由达标。客户端成功尝试的延迟判据在多轮通过，仍不能补足服务端缺失证据。原始失败结论保持，下一轮应先修解析再复测。

此外，多轮出现 `round-drain-timeout`，部分最终清理却为 0 异常，说明“结束时查到已清理”与“在要求的时间内收尾”必须分别判断。不能用最终状态抹掉等待超时。

上述分位按原始 elapsed 排序、nearest-rank 计算；HTML `statistics.json` 的分位估算略有差异，应注明算法。原 JMeter README 的“读 71,999”有一条计数误差，“226 GET/s”未说明窗口；本次采用可重算的全读取窗口值。

该计划是 80 条 HTTP 读取线程、320 个登录账号轮用，只覆盖列表两页和 pending，未执行 WebSocket 对局，也不覆盖 overview/rounds。因此可证明这组读流量下 HTTP 表现良好，不能据此宣称验证了 320 人同时对局容量。它与自研工具的低延迟方向一致，但两者路由、发压模型和服务端负载不同，不构成严格同画像 A/B。

当前 JMX 的节奏是每次等待 333 ms 再发送，响应耗时会降低实际请求率；`DURATION` 在 scheduler=false 时不是硬性结束时限，实际由 80×900 次迭代控制，`GET_PER_SEC` 变量也未驱动定时器。复现应报告实际吞吐和实际窗口。令牌 CSV 使用追加写入，重复运行前需使用新文件或显式清理旧测试令牌；目前没有逐接口业务成功断言，HTTP 200 不能独立证明业务数据正确。
