# 海南麻将并发能力提升计划书

版本：1.0 ｜ 日期：2026-10-09
项目：HainanMaJhong2 ｜ 线上站点：jiangpahnmj.cn
适用配置：2 核、2 GB、10 Mbps 公网出带宽；Spring Boot、MySQL、Redis、Nginx、Vue。

## 一、建议与目标

推荐顺序：**补齐监控与房间关闭保护 → 战绩分页、按需加载和 HTTP 压缩 → 战绩查询与缓存优化 → 同条件验证带宽、机器升级 → 按房间归属扩展多节点。**

优先解决“历史越来越长，一次查询返回越来越多数据”。只扩带宽可以缓解当前压力，但不能解决请求大小随历史增长的问题；只加缓存可以减少数据库工作，却仍然要发送同样多的数据。

第一阶段工程目标是：**256 名活跃玩家、64 桌，同时持续对局和查看战绩，在明确的负载与响应标准下稳定运行。**这是待验收目标，不是当前容量承诺。下一阶段可将 512 人作为候选目标；是否启动，由第一阶段结果和业务需求决定。

当前临时运营建议为 144 名活跃玩家、36 桌，给本次已通过的 192 人档位保留约 25% 余量。这个值适用于本次测试负载，未经长时间验证，也未写入线上配置。闲置在线人数、纯对局人数与混合活跃人数应分开公布。

## 二、现状与证据

### 2.1 已测出的边界

|档位|实测表现|用于计划的结论|
|---|---|---|
|192 人 / 48 桌|5 分钟、36,000 次查询、零失败；最慢接口 P95 约 39 ms|已验证短时通过；仅一次正式公网验证|
|208 人 / 52 桌|首次通过，复测末段失败率约 1.004%|边缘档位，不能当稳定运营上限|
|216 人 / 54 桌|两轮总体基础验收通过，末段均退化|总体平均指标会掩盖持续恶化|
|224、256 人|末段超时集中，触发持续异常停止|当前混合负载下不稳定|

本次负载是四人真实快速对局，行动间隔约 100–300 ms，每桌每秒 2.5 次战绩/房间查询，即每人每秒 0.625 次。多次查询包含完整战绩明细，历史会随连续对局增长。这是压力模型，**不是已观测到的真实玩家固定查询频率**。前端目前主要在进入页面、点击和翻页时查询。

### 2.2 瓶颈判断

现有证据主要指向公网出带宽和大响应传输：高档位 eth0 平均流出接近 10 Mbps，HTTP 响应体接收出现超时；游戏广播 P95 仍为几十毫秒。CPU 平均约 48%–61%，最高约 73%，没有观察到全机 CPU 长期打满。

但 eth0 计数不是云厂商限速计数，包含协议开销、重传及可能的短时突发；未取得云端限速/丢包证据。因此“带宽是主要瓶颈”是较强推断，仍要通过固定其他条件的带宽 A/B 测试确认。

系统实际可见内存约 1.57 GiB，JVM 最大堆约 404 MiB；测试最低可用内存约 279–336 MiB。MySQL 与 JVM 共机，继续增大堆、数据库连接池或线程池可能挤压系统余量。不能把当前 CPU 有余量解释为所有内部队列都没有阻塞。

### 2.3 已定位的代码重点

|模块|发现|改造方向|
|---|---|---|
|RecordsServiceImpl.selectDetail|读取整场全部小局，构建总览和完整明细|拆分总览、分页小局、单局详情|
|GameRoundsMapper.selectRoundsAll|返回全部小局及四名玩家的分数、牌型等数据|先分页小局 ID，再关联四人记录|
|GameSessionsMapper.selectRecordsList / selectTotals|按 player_ids JSON 查参与记录；按历史小局汇总分数|验证执行计划；参与关系表、持久化汇总|
|战绩昵称读取|每次请求内去重，仍可能多次查用户表|批量读取，必要时加有界缓存|
|RoomSnapshotServiceImpl / RoomSnapshotRepository|快照保存与删除缺少可见的生命周期版本保护|关闭标记、版本校验、禁止旧任务写回|
|RoomServiceImpl / RoomRegistry|关闭状态与合法局间状态需要区分；恢复会注册房间|恢复前验证关闭状态、成员、会话归属|
|RoomManager / RoomRegistry|存在每房间调度器、全局同步入口|先测线程和锁，再决定共享调度、缩小锁范围|

压测清理曾发现空成员房间快照残留，已清理本次测试房间。产生原因尚未完全证明，“删除后旧保存任务写回”属于需要复现的候选原因。此问题必须先修，避免扩大并发后出现更多错误恢复。

## 三、阶段 P0：正确性保护与可观测性，预计 2–3 个工作日

### 3.1 修复房间生命周期

1. 将“暂时处于局间”和“永久关闭”区分，增加明确的关闭状态。不能把所有 BETWEEN 房间直接禁止恢复，合法四人局间房间仍应可恢复。
2. 为一次房间生命周期分配 generation，并绑定 sessionId。房间码可复用，不能只用六位房间码判定缓存、旧消息与保存任务是否仍有效。
3. 保存、关闭和退出在同一房间串行执行范围内决定顺序；异步保存携带 generation 与版本，关闭后拒绝旧版本保存。
4. Redis 中增加关闭保护，使用短小的原子条件更新完成“校验版本后写入”或“标记关闭并删除快照”。关闭保护的存活时间应覆盖旧任务最大存活期；新一代房间不能被旧保护误伤。
5. 恢复前核对关闭标记、数据库结束状态、成员合法性和会话归属。删除失败应记录并有限重试，不能静默当作成功。
6. 取消房间计时任务，检查调度器释放；广播和持久化回调都校验生命周期。

Redis 脚本可以提供原子条件更新，但运行期间会阻塞其他活动，因此只放有限的版本判断与读写，不放扫描和大循环。[Redis 官方说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

验收：并发保存/退出/解散、延迟保存、重复结束、服务恢复、房间码复用均不能复活已关闭房间；合法局间房间仍能恢复；结算不能重复计入。测试采用专用房间和账号。

### 3.2 建立一张容量监控面板

|层面|必须记录的指标|用途|
|---|---|---|
|业务|活跃玩家、活跃桌、闲置连接、每秒行动、小局结算、结束失败|把人数与实际工作量对应|
|HTTP|分接口请求量、失败率、P50/P95/P99、响应字节、首字节及完整接收时间|区分查询慢和传输慢|
|WebSocket|握手失败、四人送达延迟、断线、发送队列长度|检测游戏体验与慢客户端|
|JVM|堆/非堆、GC 暂停、线程、阻塞、任务队列|验证计算、锁与内存瓶颈|
|数据库|慢查询、执行计划、连接池等待、活跃连接、事务耗时|避免盲目扩大连接池|
|Redis|延迟、内存、命中率、过期/淘汰、保存被拒绝次数|观察缓存与关闭保护|
|主机与云网络|CPU、可用内存、磁盘、FD、流出、重传、云带宽利用率/丢包|确认资源限制|

主机与延迟指标尽量按 5–10 秒采集，云监控同时留存。日志只记录请求标识、房间生命周期标识和耗时，不记录密码、完整令牌或无必要的私人牌面。

上线前保留基线：各接口响应大小分布、单人平均出流量、数据库耗时和发送队列。后续每项改造都用这些指标解释收益。

## 四、阶段 P1：限制传输量，预计 3–5 个工作日

### 4.1 拆分战绩接口

新增兼容的 v2 接口，保留旧接口供过渡，前端通过开关切换：

- **战绩列表**：分页返回会话、参与者、最终/当前分数等摘要，不包含全部小局。
- **战绩总览**：返回总分、排名、胜局数、最高番等固定大小字段，并带当前版本。
- **小局列表**：默认每页 10 局，服务端最大 50 局；先取小局 ID，再关联每局四人的分数，避免把一局四人的记录切断。
- **单局详情**：展开某局后，再取牌型、胡牌手牌及大字段。
- **新增小局**：用最后已读小局号/游标获取增量，结合版本重读总览；不反复拉取全部历史。

所有接口先鉴权，再读缓存；分页使用稳定的 sessionId 和顺序键。定义读取截止小局或版本，避免分页过程中继续结算造成重复、漏局或总览与明细口径不一致。服务端校验分页参数并设置硬上限。

同一会话持续再战时，不能默认每四圈就是新 session。若将来调整会话划分，要另外设计历史展示和跨会话统计迁移，不能作为此次分页的隐含改动。

**验收**：10、100、1,000 小局的会话，列表与分页响应大小不随总历史线性增长；每局四人齐全，分数与旧接口一致。总览计算也要逐步摆脱全量历史扫描，而不仅是减少返回字段。

### 4.2 调整前端加载方式

先显示总览和第一页，用户翻页/展开时再加载；结算完成后失效相关缓存并刷新必要数据。合并重复点击产生的请求，页面不可见时停止非必要刷新，失败时采用有上限的退避。刚结束的小局应能立即读到已提交结果。

原前端没有被证实存在固定高频轮询，因此不把“关闭不存在的轮询”作为收益。减少的是大明细读取和重复动作。

### 4.3 HTTP JSON 压缩

先在测试环境验证 Nginx 对目标 JSON 响应启用 gzip，压缩级别从 1–3 比较，设置合适的最小响应长度和 Vary。客户端发送 Accept-Encoding，并验证解压后数据一致；统计压缩后的字节和主机实际出流量。

Nginx 的 gzip_types 默认只有 text/html，JSON 需要明确配置。记录压缩率，同时检查 CPU 和响应时间；实际收益由响应内容决定。[Nginx gzip 官方文档](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)

原压测程序未声明 Accept-Encoding，因此旧结果不能证明浏览器请求是否已得到同样的压缩。后续分别保留无压缩基线与支持压缩的客户端测试。

HTTP gzip 不会自动压缩 WebSocket 帧。本阶段不依赖 WebSocket 压缩收益。私人战绩不能加入面向公众的共享 CDN 缓存；静态资源可单独配置版本化缓存，只有实测静态下载占比高时才考虑 CDN。

## 五、阶段 P2：降低数据库和序列化成本，预计 3–5 个工作日

### 5.1 查询结构与索引

先核对线上 MySQL 版本、现有索引、数据量和代表性执行计划，再决定 DDL：

1. 批量读取一页涉及的用户昵称，避免每个参与者各查一次。
2. 候选参与关系表：session_id、user_id、seat；按 user_id 与 session_id 建适合历史分页的索引。采用分批回填、事务内双写、结果比对，再切换读路径。
3. 核对 game_rounds 的 session_id、round_num 索引/唯一性，以及分数表的 round_id 与玩家唯一性。先查重复数据和现有约束，不能直接叠加索引。
4. 用生产规模的长历史数据验证查询读行数与耗时；避免只用空库证明性能。

当前 JSON_CONTAINS 查询需要验证，不应直接认定无法使用索引：MySQL 8.0.17 起支持部分 JSON_CONTAINS 查询使用多值索引。参与关系表是便于分页与维护的候选方案，而非未验证就必须实施的结论。[MySQL 官方说明](https://dev.mysql.com/doc/refman/8.0/en/json-search-functions.html)

### 5.2 持久化战绩汇总

将每名玩家每个会话的总分、胜局数、最高番等汇总保存为小规模记录。结算明细和汇总在明确的事务边界内保持一致，避免每次打开列表重新累计所有小局。

重复结算、重试或覆盖已有小局时，不能重复累加。使用小局唯一标识与幂等更新；发生修改时计算差额或重建该会话汇总。回填汇总后逐会话校验总分与现有明细一致，核验通过才切换读取。

### 5.3 有界缓存

- 已完成小局的公共详情可缓存，键包含 sessionId、小局标识和版本。
- isMe、本人排名等用户相关字段，鉴权后再组合，或者使用含用户 ID 的缓存键；禁止把甲用户的视角直接返回给乙用户。
- 正在进行的总览可采用短 TTL，但结算提交后主动失效；保证玩家查看刚结算记录的一致性。
- 限制缓存条目、单条大小和总内存，合并同键并发回源，给过期时间少量随机偏移。
- 缓存异常时回退数据库；不能用缓存代替账目事实来源。

保留当前数据库池作为基线。只有池等待明显、数据库仍有余量时才调整，不能把线程上限与连接池同时扩大来“提高并发”。

## 六、阶段 P3：根据测量决定资源升级，预计 2–3 个工作日加长测

### 6.1 带宽对照测试

先在 10 Mbps 完成分页、压缩等改造的复测，再固定版本、账号、历史规模、查询频率、发压位置和服务器规格，对比 10 与 20 Mbps。带宽调整产生费用，实施前以云控制台实际报价确认。

对照重点：相同人数时的尾段延迟、完整响应时间、流出、重传、CPU 与失败率。若提高带宽后传输超时显著改善，而 SQL/CPU 基本不变，带宽瓶颈证据增强；若改善有限，转查连接、发送队列、锁、数据库和压测端。

不要在同一轮同时升级机器、调整连接池和改接口，否则无法判断收益来源。带宽翻倍不等于人数翻倍。

### 6.2 机器规格决策

|测量结果|下一步|暂不优先的动作|
|---|---|---|
|出带宽长期接近上限，CPU/数据库健康|验证 20 Mbps，必要时再评估更高带宽|直接上多节点|
|分页压缩后 CPU 长期高，GC/排队明显|评估 4 核、4 GB；依据内存工作集选择更大内存|在当前小机器盲目加堆|
|MySQL 执行慢、读行数大|先查询与索引、汇总优化|先把连接池翻几倍|
|SQL 已优化，但数据库与应用资源争抢|评估数据库独立部署，先验证备份恢复与连接延迟|未经验证就迁移线上数据|
|锁等待/线程随桌数增长|分析房间串行执行、调度器与同步入口|以 CPU 总利用率判断没有问题|

4 核 4 GB / 20 Mbps 是可评估的升级组合，不是预定采购或容量保证。新 JVM 堆大小根据实际可见内存、数据库工作集和监控决定，给系统、非堆和网络缓冲留空间。

### 6.3 容量计算口径

初步估算：

`出带宽需求 ≈ 活跃人数 ×（每人游戏广播 bit/s + 每人查询次数/s × 平均压缩响应字节 × 8）+ 登录/静态下载/后台流量 + 协议及重传开销`

10 Mbps 的理论速率约为 1.25 MB/s，但不能全部规划成业务响应体。运营建议保留约 25% 余量，并依据实际尖峰调整。

最终运营人数取带宽、CPU、内存、数据库、连接/FD 和体验标准共同允许的最小值。公式用于解释与预算，最终人数必须以长时间外网测试验证。

## 七、单机内部优化的触发条件

只有监控证明相关开销明显时，才做以下改造：

1. 检查每房间调度器是否结束后释放；必要时使用共享有界调度器，保持同房间事件串行顺序。
2. 检查 RoomRegistry 全局同步区域中的 Redis/恢复工作；缩短持锁区间，按房间协调创建与恢复，避免同房间重复注册。
3. 对 WebSocket 慢客户端设置有界发送队列和重连恢复机制。关键行动与结算事件不能随意丢弃；可以合并的状态快照必须带序列号并能重新同步。
4. 区分游戏推进与慢查询任务，限制查询排队。数据库写入若移到独立执行器，必须保持事务、顺序和提交确认，不能发送“结算成功”后才无保障地写库。
5. 实测 Nginx、系统 FD 与代理上下游连接数量后调整连接限制；不能只计算玩家连接而忽略上游连接。

控制容量时优先限制新开桌和非关键战绩查询。采用账号维度的查询限制和明确的重试提示，避免按 IP 误伤同一网络的多人；已开局玩家应优先保障完成对局。

## 八、阶段 P4：达到单机边界后再实施多节点

启动条件：单机优化及合理资源升级后，仍不能满足目标人数，或者业务明确要求应用节点故障时可恢复。

当前房间状态、WebSocket 会话与锁主要在应用内存。**增加两台应用并轮询转发，不能自动得到正确的多人麻将集群。**需要以下设计：

- 建立 roomId/generation → ownerNode 的房间归属目录。
- 开桌、入桌、游戏连接和重连均路由到同一拥有者；战绩查询可作为独立无状态服务扩展。
- 每个房间只有一个有效执行者，归属租约配合单调递增的 fencing token；旧节点失去归属后不能继续结算或写快照。
- 定义动作序列、持久化进度与恢复点，先验证节点失效时恢复到哪里、哪些未确认动作需要重试。
- 数据库结算幂等；Redis 保存快照和目录并不等于共享了实时游戏引擎。
- 扩容只把新桌分给新节点；活动桌迁移另行设计和验证。

建议先拆战绩读流量，再考虑拆房间节点。预计额外 2–4 周用于归属、路由、恢复和故障测试，具体取决于可接受的中断与恢复要求。千人容量需要另外验收，不能由单机结果线性外推。

## 九、统一测试与验收标准

### 9.1 测试矩阵

|场景|用途|执行方式|
|---|---|---|
|纯游戏广播与结算|测游戏路径本身的容量|四人独立账号，持续真实行动，不高频查战绩|
|战绩查询专项|比较查询、序列化与传输|固定历史数据与查询分布，记录响应字节|
|原混合基线|保留与旧测试的可比性|0.625 查询/人/秒、原行动节奏与五类查询|
|新版业务等价混合|验收分页和按需加载后的体验|相同查看需求，公开实际请求数、字节和分页深度|
|真实使用模型|测运营容量|依据真实访问记录校准进入页面、翻页和展开频率|
|长历史|排除数据增长后的退化|10/100/1,000 小局及不同历史会话数|
|登录/重连/下载突发|测试平稳人数之外的尖峰|逐步增加同时进入比例，先在隔离环境验证|
|慢客户端和节点故障|验证队列和恢复正确性|隔离环境注入网络故障、进程退出、延迟保存|

新版分页改变请求组合后，必须同时报告每人请求量、传输量和完成的查看动作，不能通过减少业务工作量宣称同条件容量提高。

阶梯建议：144 → 192 → 224 → 256 人，遇到退化在边界附近细分。先用短测排除明显失败档位，再对目标档位做 **3 次独立 30 分钟混合测试**，最后在拟定运营档位做 **至少 8 小时长测**。更高目标另行递增验证。

尽量使用两台独立公网发压机，确认直连，并监控发压端事件循环、网络和连接限制。每轮固定初始历史规模；另外保留持续增长场景，避免不同数据量污染 A/B 结论。

### 9.2 建议的新验收目标

以下是拟定的新工程标准，区别于旧报告的基础门槛：

|项目|目标|
|---|---|
|战绩查询|各接口 P95 ≤500 ms，P99 ≤2 s|
|四人关键广播送达|P95 ≤150 ms，P99 ≤500 ms|
|连接建立|P95 ≤1 s，P99 ≤3 s|
|失败率|每个滚动 5 分钟 ≤0.1%；每个滚动 1 分钟 ≤0.5%|
|业务正确性|漏结算、重复结算、分数/成员错误、关闭后复活均为 0|
|增长趋势|堆、线程、队列和单页大小不存在持续无界增长|
|运营余量|在拟定运营档位，资源与体验仍有余量；带宽和 CPU 通常争取不长期超过约 75%|

分接口统计，不能用全站平均掩盖慢明细。公布全程与末段数据；停止发压后等待已发请求完成或超时，尾段按发起时间核算，避免漏掉未完成请求使结果偏好。非预期业务失败也计入结果，不能仅检查 HTTP 状态。

安全停止沿用当前规则作为最低保护：最近 20 秒请求完成窗口达到足够样本时，失败率 >5% 或 P95 >5 秒，连续两次触发停止；另加资源持续恶化与业务正确性错误保护。因为完成窗口可能遗漏仍在等待的请求，还必须观察在途数量和请求年龄。测试停止后核对结算、结束时间和专用房间清理。

若 256 人通过验收，192 人可作为保留 25% 人数余量的候选运营档位，但还必须通过该档位长测与真实使用模型；512 人通过后同理评估 384 人。余量比例不是稳定性的替代证明。

## 十、发布与回退

1. **准备**：建立与生产版本一致的测试环境，备份数据库并验证恢复；冻结基线版本与负载参数。
2. **兼容改造**：新接口、字段和表采用增量方式；回填可暂停、可重跑，先比对再切换。暂不删除旧结构。
3. **小流量验证**：先让专用账号/少量新桌走新路径，观察指标与分数一致性，再逐步扩大。
4. **部署游戏服务**：停止接新桌、等待活动桌结束，或采用已经验证的恢复流程。现阶段不能承诺任意重启都无损，必要时使用明确维护窗口。
5. **Nginx 配置**：先校验配置再平滑重载；长连接旧进程可能保留，需观察 FD 与内存，不能把 reload 当作所有连接瞬间迁移。
6. **回退触发**：错误率/延迟持续超标、数据不一致、关闭后复活、内存或队列持续增长。
7. **回退执行**：关闭新版读路径/缓存开关，恢复兼容实现；旧全量明细仍要保持保护限制，不能重新放大流量。新数据库结构保留，先停止错误写入，再按幂等记录修复。
8. **升级回退**：带宽或规格降回旧配置前，确认当前负载在旧配置可承受范围。扩容与降配均独立留存测试结果。

正确性失败应优先暂停新开桌并保全记录，不能只靠增加资源掩盖。测试清理限定为专用账号和本轮房间，不批量删除业务战绩。

## 十一、排期、投入与决策点

排期假设：一名熟悉项目的后端工程师主导，前端工程师参与分页页面，测试/运维参与监控和复测。现有代码熟悉度、测试环境和迁移数据量会影响工期。

|时间|工作|交付与进入下一步的条件|
|---|---|---|
|第 1–3 天|P0 生命周期修复、指标与基线|竞态测试通过，能够定位延迟与流量来源|
|第 3–7 天|P1 总览/分页/详情、前端、压缩对照|历史增长不再放大单页数据，旧新账目一致|
|第 6–10 天|P2 批量查询、汇总、缓存和迁移比对|长历史 SQL 与缓存行为达标|
|第 11–14 天|P3 256 人复测、必要的带宽单变量对照|取得重复测试结果和资源升级建议|
|第 15 天起|运营档位长测、灰度与报告|满足验收后才提高运营控制值|
|后续按需|P4 房间归属与多节点|单机不能满足需求或需要节点故障恢复|

单机阶段按 **2–3 周窗口**安排，实际有效工程投入预计约 15–25 人日，作为计划估算而非报价。发现结算事务或恢复机制需要大幅修改时，应调整范围与排期。第一轮可先完成“监控 + 房间关闭保护 + JSON 压缩验证”，再推进分页主线。

预算分为三项：开发/测试投入、测试环境及临时带宽费用、长期云资源费用。云资源价格以地域、实例和计费方式的控制台报价为准，本计划不编造月费。先得到改造后的单位玩家成本，再决定长期购买规格。

每次购买前的决策材料应包含：目标人数、当前已验证档位、瓶颈证据、候选规格报价、同条件预期验证方法，以及停止/回退条件。

## 十二、交付清单与完成定义

- 房间生命周期竞态复现、修复及关闭/恢复测试。
- 分页战绩接口、前端按需加载和兼容切换开关。
- 经比对的汇总与参与关系迁移方案，包含回填和回退步骤。
- HTTP 压缩 A/B 结果、响应大小与实际流量报告。
- 分层监控面板、容量告警和新开桌控制方案。
- 固定版本的压测脚本、场景数据、请求口径和清理说明。
- 256 人目标档位的三轮结果、运营档位长测结果、上线回退记录。
- 最终推荐运营人数和资源成本；明确纯对局、混合活跃、闲置连接三个口径。

完成定义：正确性通过、目标场景达到约定标准、长测没有持续退化、回退可执行，才宣布并发能力提升完成。代码合并、购买更大带宽或某一轮短测通过，都不是单独的完成依据。
