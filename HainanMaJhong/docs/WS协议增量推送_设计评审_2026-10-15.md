# WS 推送协议设计评审：从"每次动作全量重推"改为"事件 + 增量"（2026-10-15）

对应《WS推送量归属_2026-10-15》的下一步。**本文档只做设计评审，不改任何代码。** 结论：可行、收益约 0.10 个核（全机 ≈8%），但有明确的契约与兜底要求；建议分两阶段，先做低风险的一半。

## 一、目标与范围

- **目标**：削减"客户端可由已收到的事件推导的状态"被反复整份推送的量。实测三者占 WS 字节 68%、发送量 59%：`counts`（37.6%）、`hand`（16.4%）、`turn`（14.4%）。
- **范围**：WS `/game` 端点的服务端推送；`/room`（等待房）不动。前端在仓库内（`frontend/src/stores/game.js`），压测工具也在仓库内（`docs/performance/online-capacity-retest.mjs`），三处可同步改。
- **非目标**：不改变 HTTP 战绩接口、不改 Redis 结构、不改结算与规则判定、不碰 P2 读路径。

### 2.2 客户端已经做到的增量维护（重要）

`frontend/src/stores/game.js` 里这几条已经把"事件 → 状态"的推导做了一半：

- `onDiscard`（:458-469）：**把打出的牌追加进 `boardDiscards[seat]`** —— 牌河已经是增量维护的（注释明确写了"board 只在重连时下发"）。
- `onMeld`（:483+）：按后端语义**替换**补杠（不是无脑 push）。
- `onFlower`（:436-449）：追加进 `boardFlowers[seat]`。
- `onHand`（:405-415）：把自己的手牌与 melds/flowers 设为**权威**（因为 meld 广播可能丢）。
- `onCounts`（:398-402）：`counts` = 各家手牌张数（画牌背）+ `wall`（中后段才带）。
- `onTurn`（:422-425）：`turnSeat` + `timeoutMs`（高亮与倒计时）。

**结论**：牌河/副露/花已经不需要全量推送；真正的冗余集中在 `counts`、`turn`、以及每次动作重推的 `hand`。

### 2.3 压测工具的依赖（决定 A/B 可行性）

`online-capacity-retest.mjs` 的逻辑消费 **仅有**：`welcome`、`hand_start`（把 `m.hand` 当作**局号**用）、`request`（用 `m.hand` 手牌 + `m.ban` 选牌）、`discard`（座位/牌面/四家送达校验）、`coins`（结算零和）、`meld`（暗杠不得外泄）、`match`/`match_finish`、`room_closed`、以及入房时的 `board`+`hand`（重连检查）。

**它完全不消费 `counts` 和 `turn`**，也不在每手动作里等 `hand`。→ **Phase 1 的改动对压测工具逻辑零影响**，只需在 URL 上加开关参数并利用它已有的 `messageCounts[m.type]` 做对照统计。

## 三、设计原则

1. **不发明新事件**：能折叠进既有事件的信息就折叠（`turn` 折进 `draw`/`discard`/`meld`），不新增"更小的 counts 消息"。
2. **权威快照永不失联**：任何时刻客户端都能通过一次全量快照回到正确状态（入房、重连、定期、显式请求）。
3. **可检测漂移**：推送带单调序号，客户端发现缺口就请求重同步。
4. **按会话独立生效**：同一房间里允许"增量客户端"与"全量客户端"共存（旧版本客户端不受影响）。
5. **先低风险后高风险**：先动"对手视图"类信息（counts/turn），再动"自己的手牌"（hand）。

## 四、逐消息决策表

| type | 决策 | 理由与风险 |
|---|---|---|
| `counts` | **Phase 1：取消每动作推送**；改为 ①入房/重连/定期全量快照 ②把"手牌张数变化"折叠进 `draw`/`discard`/`meld`/`flower` 事件（新增字段 `handSize`：本家张数；以及 `sizes` 仅在必要时） | 对手手牌张数=13−副露+摸/打，理论可推导；但**折叠比推导更稳**（服务端直接给出，客户端无需实现补杠/暗杠的减张规则）。风险低：只影响对手牌背数量显示 |
| `turn` | **Phase 1：取消独立推送**，把 `seat`+`timeoutMs` 折叠进 `discard`/`draw`/`meld`（`nextSeat`、`timeoutMs`） | turn 与事件一一对应（实测 51 次/局 ≈ 打牌次数）。风险低：影响高亮与倒计时；折叠后信息量不变 |
| `hand`（每动作） | **Phase 2：降频 + 对账**。保留：`hand_start` 后、入房/重连、每次暗杠/补杠/花牌后、以及每 N 秒（建议 5 秒）或每 M 个动作的周期性对账；**取消**每动作必推 | 这是"自己的手牌"，显示错误最敏感。客户端可维护（draw 加牌、discard 去牌、meld 去牌），但必须有对账兜底。收益 16.4% 字节 |
| `draw`/`discard`/`meld`/`flower` | **保持**（并作为 `turn`/`counts` 的载体） | 真实事件、最小集，压测工具也依赖 |
| `request` | **保持** | 服务端规则判定，不可推导；压测工具用它选牌 |
| `board` | **保持并强化**：入房、重连、定期全量、客户端请求重同步时下发 | 兜底机制的核心 |
| `hand_start`/`coins`/`end`/`hu`/`match*`/`room_*` | **保持** | 低频且必要 |

## 五、新契约定义（服务端 → 客户端）

### 5.1 新增字段（折叠，不新增消息）

```
discard  : { type, seat, tile, nextSeat, timeoutMs, handSize }   // nextSeat/timeoutMs 原 turn 的内容
draw     : { type, seat, tile, nextSeat, timeoutMs, handSize }
meld     : { type, seat, meld, nextSeat, timeoutMs, handSize }   // 暗杠仍按 viewer 隐藏 tiles
flower   : { type, seat, tile, handSize }
```
- `handSize` = **该事件的发起者**在事件发生后的手牌张数（客户端用它更新"对手牌背数量"，本家的手牌另行由 `hand`/推导维护）。
- `nextSeat` = 事件处理完之后轮到谁（与原 `turn.seat` 同义）；`timeoutMs` 与原 `turn.timeoutMs` 同义。
- 可选：`wall`（牌墙剩余）只在 `hand_start` 与定期快照里给，不从每动作事件推。

### 5.2 序号与缺口检测

```
每条 /game 推送增加 seq: { ..., seq: 12345 }   // 房间内单调递增，从 welcome 开始
```
- 客户端发现 `seq` 跳号 → 立即发 `{type:"resync"}`，服务端回 `board` + `counts` + `hand` 全量。
- 服务端对同一连接**按序发送**（现有 `synchronized(session)` 已保证单连接不交错）。

### 5.3 客户端新消息（上行）

| 消息 | 语义 |
|---|---|
| `{type:"resync"}` | 请求全量快照（服务端回 board+counts+hand）。**限频**（例如每 5 秒最多 1 次），避免被滥用放大流量 |

### 5.4 兼容性语义

- 不认识的字段（`nextSeat`/`handSize`/`seq`）旧客户端会忽略 ✓（JSON 额外字段无害）。
- 旧客户端继续收 `counts`/`turn`（因为它握手时声明 `push=full`）。

## 六、开关与兼容矩阵

- **握手参数**：`/game?code=..&seat=..&token=..&push=full|delta`（`WsAuthHandshakeInterceptor` 已解析 query 参数，扩展一处即可；写入 `session.getAttributes()`）。
- **默认值**：服务端默认 `full`；配置项 `PUSH_DEFAULT=delta` 便于灰度切换（前端发版后翻转）。
- **混合房间**：`broadcastGame` 的循环内**按 session 属性决定是否发送**被裁掉的类型；同一条 payload 仍只编码一次，只在"需要它的人"那里发送。
- **回滚**：把 `PUSH_DEFAULT` 改回 `full` 并重启（或让前端不发 `push=delta`），前端无需回滚（它必须同时兼容两种模式）。

## 七、兜底与重同步（这是本设计的安全底线）

| 时机 | 动作 |
|---|---|
| 入房 / `welcome` | 全量 `board` + `counts` + `hand`（现状已如此） |
| 断线重连 | 同上（现状已如此） |
| **定期** | 每 5 秒（或每 10 个动作，取先到者）推一次全量快照给"增量模式"客户端 |
| 客户端 `resync` | 立即全量 |
| 服务端检测到发送异常/连接抖动 | 重连后自然全量 |
| 每局开始（`hand_start`） | 全量（本局起点权威） |

**漂移可观测**：建议服务端计数 `mahjong.ws.resync`（按原因分标签：periodic/client-request/reconnect），用于灰度期观察漂移频率——如果周期性重同步之外的重同步频繁，说明推导规则有漏洞。

## 八、前端改造清单（`frontend/src/stores/game.js`）

1. 握手 URL 增加 `push=delta`（灰度期可由配置控制）。
2. `onDiscard`：除现有追加牌河外，用 `m.handSize` 更新 `counts[m.seat]`；用 `m.nextSeat` 更新 `turnSeat`、`m.timeoutMs` 更新倒计时。
3. `onDraw` / `onMeld` / `onFlower`：同样消费 `handSize`/`nextSeat`/`timeoutMs`。
4. `onCounts` / `onTurn`：保留（全量模式仍会收到），但改为"增量模式下来不到也不报错"。
5. **Phase 2 才有**：维护自己的手牌（`draw` 加、`discard` 去、`meld` 去对应张数、`flower` 不动手牌），并用周期性 `hand` 对账；对账不一致时以 `hand` 为准并记一条告警。
6. `seq` 缺口检测 + `resync` 发送（限频）。

## 九、压测工具改造清单（`online-capacity-retest.mjs`）

1. 连接 URL 增加 `push=delta`（用环境变量 `TEST_PUSH_MODE` 控制，默认 `full` 以保持历史可比）。
2. 逻辑**无需改动**（不消费 counts/turn；`hand` 仅入房/重连时等）。
3. 对照统计现成可用：`s.rooms[].messages`（`messageCounts` 按类型）已记录全类型计数 → 直接能出"开/关"前后的按类型对比。

## 十、验证与验收

**同条件开/关对照**（每轮固定：16 桌 60 秒预热 → 目标档位 300 秒；同账号、同 rps、同保护规则）：

| 维度 | 指标 | 期望 |
|---|---|---|
| 流量 | WS 发送次数/秒、按类型计数、WS 字节/秒 | Phase 1 发送 ≈ 4,796 → **≈2,390/s（−50%）**、字节 ≈ 343 → **≈165 KB/s（−52%）** |
| CPU | `process_cpu_usage`/`system_cpu_usage` 均值与峰值、`mahjong.ws.send` 累计耗时 | 发送路径 CPU 约 −0.085 核（Phase 1） |
| 延迟 | HTTP P95/P99、广播确认延迟（end/hand_start/coins 均值）、广播 P95 | 不劣化（允许 ±5%） |
| 正确性 | 结算局数、四家分数零和、暗杠不泄漏、四家送达一致、`dupReq=0`、清理审计 | 全部与全量模式一致 |
| 漂移 | `mahjong.ws.resync` 计数（分类） | 周期性重同步之外应接近 0 |

**业务层**：另需**人工/脚本回放**验证前端渲染（牌河、副露、牌背数量、倒计时、手牌）在增量模式下与全量模式逐帧一致（建议做一段录制回放对照）。

**通过后再做**：320 人 3×30 分钟 → 336/352/368/384（遇首个失败停止）。

## 十一、风险与缓解

| 风险 | 缓解 |
|---|---|
| 前端状态漂移（尤其自己的手牌） | Phase 2 才动 `hand`；周期性全量对账；`seq`+`resync`；灰度期观察 resync 计数 |
| 补杠/暗杠/花牌的张数语义复杂 | 由**服务端给 `handSize`**，不要求客户端实现规则 |
| 混合模式房间行为不一致 | 发送循环按 session 属性分支；测试用"1 增量 + 3 全量"的混合房间 |
| 压测工具与线上契约分叉 | 开关放 URL，工具默认 `full`；A/B 时显式切换并记录模式标签 |
| 流量下降但延迟变差（例如快照太重） | 定期快照频率可调；对照 P99 与广播确认延迟 |
| 回滚不干净 | 服务端默认值一键回 `full`；前端两种模式都兼容 |

## 十二、分阶段计划

| 阶段 | 内容 | 预期收益 | 风险 |
|---|---|---|---|
| **Phase 1** | 握手开关 + `counts` 取消每动作 + `turn` 折叠进事件 + 定期全量 + `seq`/`resync` | **−50% 发送量、−52% WS 字节 ≈ 0.085 核** | 低（只动对手视图/高亮） |
| **Phase 2** | 每动作 `hand` 降频 + 客户端手牌推导 + 周期对账 | 再 −9% 发送量、−16% 字节 ≈ 0.015 核 | 中（自己的手牌显示） |
| **Phase 3**（可选） | 用同一套 `seq`/快照机制评估更多"可推导"内容（如 `wall`、`drawnTile` 的重复下发） | 待测 | — |

## 十三、预期收益与边界（务必如实）

- Phase 1+2 合计约 **−0.10 个核 ≈ 全机 8%**（320 人档），加上已上线的序列化复用（0.024 核）约 **0.12 个核 ≈ 9–10%**。
- **这仍不足以保证 400 人通过**：400 人失败时 CPU 在 0.9+ 持续 20 秒以上，需要的是更大的余量。收益要**实测**，不要承诺。
- 若目标是"400 人可持续"，在软件优化之外仍应把 **vCPU 2 → 4** 作为并行选项评估（两者不冲突）。

## 十四、待确认的开放问题

1. 灰度期默认值：先 `full` 默认、前端发版后再翻 `delta`，还是直接 `delta`？（建议前者）
2. 定期全量快照的频率：5 秒 / 10 个动作 / 每局开始，三者的取舍（建议 5 秒 + 每局开始）。
3. `handSize` 的口径：只给"事件发起者"，还是给四家？（只给发起者可省字节，但客户端要自己算对手张数变化——建议先给发起者，配合全量快照兜底）
4. 是否需要服务端在灰度期做"双写对照"（同时按两种模式生成消息并比对内容一致性），还是只靠 resync 计数与业务断言？
5. Phase 2 是否值得做（收益仅 16% 字节、风险最高）——可先上 Phase 1 实测后再定。
