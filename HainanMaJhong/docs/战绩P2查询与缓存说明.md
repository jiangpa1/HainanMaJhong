## 数据与查询

- 昵称按请求去重批量读取，一批最多 200 个真实用户；只取 id、nickname、username。保留机器人、游客、昵称为空和账号已删除的显示规则。昵称不跨请求缓存，修改后立即可见。
- 新增 `game_session_players`，一场四行，同时保存参与关系、座位、总分、胜局数、最高番及原始番型 JSON。主键 `(session_id,user_id)`；唯一座位 `(session_id,seat)`；历史分页索引 `(user_id,session_id)`。
- 新增 `game_record_versions`，保存汇总截止局号和修订号；`session_id=0` 为全库校验门闩，业务会话必须为正数。
- 当前截止点的 V2 总览读取四行汇总，V2 列表从参与索引分页并批量读取汇总。冻结的历史截止点仍从明细 SQL 聚合，保持原分页语义。兼容旧接口保持旧总分查询，昵称批量化。
- 不新增或修改旧表索引。工具先输出 MySQL 版本、现有索引、数量、重复局、重复玩家流水、缺失四家及孤立流水；指定代表性用户和会话后输出 JSON 查询与关系查询的 `EXPLAIN FORMAT=JSON`。是否进一步调整旧索引必须依据生产输出决定。

## 事务与幂等

建场的会话、四个参与者和零汇总在同一事务提交。结算沿用会话行锁：已有小局直接返回，不重复累计；新局必须包含四个唯一玩家和座位并与会话一致。小局、四家流水、进度、汇总和修订号在同一事务写入。失败全部回滚。

未回填的旧会话首次结算时，先在相同行锁内从已提交明细重建，再追加新局。正常追加只更新四行汇总；插入较早局号时重建，保持最高番相同情况下取最早局的规则。提交后主动清理该会话的本地缓存；回滚不触发清理。小局不提供覆盖接口；人工修正明细必须先撤销门闩、关闭读路径及缓存，并用重建与比对流程恢复。

## 缓存

单局缓存保存数据库公共行，先验证会话参与权限和读取截止点，再访问缓存。键为 `(sessionId,roundNum,revision)`。每次读取解码为独立副本，再装配当前昵称和 `isMe`；不缓存用户视角。

默认单局缓存：最多 512 条、单条 64 KiB、总数据 8 MiB、TTL 60 秒并增加 0～10% 随机偏移。超限、缺少四家、序列化失败时绕过缓存。64 个固定锁合并同键回源，不创建无界锁或任务队列。回源错误不缓存，下一请求可以重试。修订号包含在响应版本中，回填或账目修正不会复用旧版本。

兼容聚合缓存最多 512 场，每场四人；缓存最高番描述最多 8 KiB，描述总预算约 4 MiB，另有少量对象开销，寿命固定 60 秒。同会话通过固定锁合并回源。修订号变化时拒绝旧缓存；新读路径的当前总览直接读取四行汇总。JVM 中缓存数据预算约 12 MiB，实际内存还包括对象、解析及响应临时分配，需用监控验证。

Prometheus 暴露 `mahjong_records_cache_entries`、`mahjong_records_cache_bytes` 以及 `mahjong_records_cache_requests_total{outcome}`，结果标签为 hit、miss、bypass、decode_error、encode_error。标签不包含会话或用户 ID。

## 分批上线与回退

默认配置：`RECORDS_P2_WRITE_ENABLED=true`、`RECORDS_P2_READ_ENABLED=false`、`RECORDS_P2_CACHE_ENABLED=true`。写开关打开时，新表必须可写；投影写入失败会回滚结算并暴露故障，不能静默丢账。启动只创建新增表，不启动回填任务。

1. 备份并验证恢复，在单实例维护流程下发布双写代码，保持新读开关关闭。先在同版本测试库运行 `inspect`，核对重复、缺失、索引和代表性执行计划；旧数据有异常时先调查，不自动删除或合并。
2. 用 `prepare` 显式建立新增表（也可由应用启动建立）。不删除或改写旧结构。
3. 每次 `backfill` 最多处理 500 场，默认 100 场；每场独立事务、锁住会话后重建并比对四个成员/座位、总分、胜局数、最高番和番型 JSON。输出 `checked` 与 `lastSessionId`。下一批使用返回的游标；`checked=0` 结束。有错误立即停止，成功场保留，可从旧游标重跑。单场事务超时为 30 秒；特别长的会话应在维护窗口处理。
4. 执行 `verify` 分批只读比对，随后 `promote` 从头再次逐场校验，核对没有遗漏会话，再建立门闩。`promote` 开始先撤销旧门闩，任何比对失败保持关闭。全库校验可能持续较久，可中断；不会删除业务明细。
5. 保持所有写入来自当前单实例、双写开关开启，再设 `RECORDS_P2_READ_ENABLED=true`。配置与门闩同时满足才使用新读路径；门闩缺失时自动走兼容 SQL。对专用账号比对旧新账目、新结算、分页和各用户视角，然后观察 SQL 耗时、连接等待、堆和 HTTP 尾延迟。
6. 读路径回退：设 `RECORDS_P2_READ_ENABLED=false`；可执行 `revoke` 立即撤销门闩。缓存回退：设 `RECORDS_P2_CACHE_ENABLED=false`。新表保留。双写故障时，在维护流程下先关闭新读与缓存，再设 `RECORDS_P2_WRITE_ENABLED=false`；恢复后全量重建、验证并重新 promote。回退旧 jar 时同样先 revoke，防止旧代码产生未双写记录后直接重新开启读路径。

生产配置仍为单实例。不要在新旧写入程序并存期间 promote；绕过 `RoundPersister` 的写入需要单独纳入事务和版本协议。

## 工具命令

从环境提供 `RECORDS_P2_JDBC_URL`、`RECORDS_P2_DB_USER`、`RECORDS_P2_DB_PASSWORD`，密码不放进命令、日志或版本库。工具不会自动读取生产凭据，不启动游戏服务或监听 HTTP。

Windows（JDK 17，已构建 jar）：

```powershell
.\ops\records-p2.ps1 -Operation inspect -UserId 123 -SessionId 456
.\ops\records-p2.ps1 -Operation prepare
.\ops\records-p2.ps1 -Operation backfill -AfterId 0 -BatchSize 100
# 下一批使用输出的 lastSessionId
.\ops\records-p2.ps1 -Operation verify -AfterId 0 -BatchSize 100
.\ops\records-p2.ps1 -Operation promote
.\ops\records-p2.ps1 -Operation revoke
```

Linux：

```bash
java -Dloader.main=hainanMahjong.ops.RecordsP2Migration \

```
