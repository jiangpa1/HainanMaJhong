# 八天并发优化：把性能结论变成可以反驳的证据

整理日期：2026-10-16。实验路径覆盖 10 月 8—15 日八个自然日；不是每天一项、严格隔离变量的八组实验。项目是简历与并发工程练习，目标是在固定小规格机器上解释性能、管理过载，并如实说明尚未证明的边界。

## 1. 目标：先定义什么叫“做好”

目标分为三层：正常画像下对局、查询和结算稳定；超载时尽早、有明确语义地拒绝；异常时有指标、停止条件和可操作的回退路径。人数是一个输入，不能单独代表容量。

早期 10/08 的 5/10 RPS 探测分别约 150/300 个响应，后者 1 次失败，P95 约 1,582 ms；后来升级为“独立账号 + 实际对局 + 战绩查询 + 结算收尾”。10/09 的 192 人窗口是 48 桌、120 GET/s、300 秒、36,000 请求、0 失败、P95 39.0 ms。这两类测试不能连成一条人数增长曲线。历史来源见[逐项对比](逐项优化与线上容量对比_2026-10-14.md)。

坑：只把“接口返回 200”当目标，会漏掉牌局结算不完整、房间无法回收和重试造成的隐性过载。

## 2. 画像：固定工作负载，再谈人数

主画像为每桌 4 个独立账号、持续 WebSocket 对局、每桌 2.5 次战绩 GET/秒。192/320/512 人分别是 48/80/128 桌，对应 120/200/320 GET/s。登录准备、预热、正式窗口、收尾分别记录，不能把登录吞吐和稳态查询吞吐混在一起。

环境经历过 10→20 Mbps 带宽、MySQL 内存调整、应用重启、P2 数据回填、4 GB swap 和保护策略调整。跨日期结果是系统演进记录，不是单项代码优化的严格 A/B。

512 人标准画像合计 320 GET/s，其中五种轮询约四种是战绩、一种是 pending，因此受战绩闸门保护的目标流量约 256 GET/s；不能把总请求和单分组请求混用。实际计数以每轮配置、端点及重试记录为准。冷、热实例也要分别报告：同为并发额度 48，冷实例 P95 12,202 ms、在途峰值 2,035；热实例 P95 261 ms、在途峰值 115。见[准入验证](准入保护验证_2026-10-15.md)。

坑：代理 TUN/fake-IP 和 SSH 采样隧道故障曾表现为容量失败；退出代理后同档位恢复。先分清发压机、网络链路、入口和业务服务，保留受污染轮次及排除理由。

## 3. 判据：开测前决定怎样算失败

P2 画像要求各接口 P95≤500 ms、P99≤2 s，四人广播 P95≤150 ms、P99≤500 ms，并检查失败率、账目一致、在途行动与房间收尾。具体完整门槛以[压测入口](../../docs/performance/README.md)和每轮配置为准；旧 baseline 使用过不同阈值，不能按新门槛重写旧 pass。

资源保护与业务验收分别记账。当前 CPU 保护采用 `system_cpu_usage > 0.95` 持续观测至少 60 秒；普通监控可用内存底线 100 MiB。触发保护代表该轮未完成，不代表找到了业务吞吐极限。缺失采样也不能当正常。

反例：10/11 V2+gzip 正式窗口完成 36,001 请求、8 次失败，但收尾发生两次连接重置，原轮严格验收未通过。事后确认房间已清理也不修改原判定。512 人最新短测 96,001 请求、0 失败、P95 229 ms，但未匹配广播约 0.101% 超过 0.1% 门槛，仍保留原始未通过。见[10/11 报告](线上压测对比_2026-10-11.md)、[极限报告](极限压力测试_2026-10-15.md)。

坑：把“性能窗口健康”和“完整验收通过”合成一句，会把协议和收尾缺陷藏起来。

## 4. 度量：记录成本、分母和观测扰动

至少同时记录：逻辑请求数、实际 HTTP 尝试数、中间与最终 429、各接口分位、广播确认、结算数、收尾耗时、在途峰值、CPU、可用内存、连接池、字节与编码次数。还要记录 jar/config 指纹、账号历史、冷/热状态、采样方式和停止原因。

现有工具对幂等 GET 的 429 最多重试 4 次并加抖动，作用不只限于准备阶段。因此历史“最终 0 个 429”不等于服务端没有拒绝；重试也会改变实际 RPS 和逻辑请求耗时。z2 有 358 次重试、最终 0 个残留 429，必须把两项一起报告。历史数据缺失原始尝试计数时明确写“未采集”，不补造。

10/15 无采样的 320 人轮 P95 45.8 ms，每 5 秒 jstack 轮升至 140.8 ms。观测器本身会影响结果。`/proc` 线程 CPU 增量可用于 CPU 归属；RUNNABLE 栈样本、socket 阻塞和 Micrometer Timer 的累计 elapsed time，不能直接当 CPU 时间。见[热点归属](热点归属_2026-10-15.md)。

坑：CPU 瞬时 gauge 与两分钟平均不是同一个量；每 5 秒读取一个约 10 秒更新的 gauge 也不等于拿到了独立样本。

来源：[V2/压缩对比](优化前后对比_2026-10-10至11.md)、[前端说明](战绩前端按需加载说明.md)、[P2 复测](线上压测复测_2026-10-12.md)、[广播复用](广播序列化复用_2026-10-15.md)、[Phase 1 报告](Phase1测试报告_2026-10-15.md)、[准入验证](准入保护验证_2026-10-15.md)。

Phase 1 报告已撤回“coins 挂起”和“seq 全项目未写入”的初版诊断：coins 是直接发送，被测包也已有 seq；只查一个文件就下全项目结论是方法错误。后续加入定时 flush、生命周期屏障与周期快照调整后，256 人 delta/full 均通过，drain 22/24 秒，发送 −46.3%、字节 −36.4%。但 320 人重复实验 delta 又出现 120.1 秒收尾失败，不能停在中途的“P0 已解决”结论。

该报告最终统计有效 320 人轮：delta 7 轮系统 CPU 均值平均 0.617，full 3 轮平均 0.613，没有可分辨的 CPU 收益。系统 CPU 比例相差 0.004，不应直接写成“0.004 个核”；2 vCPU 上若换算核数应乘 2，且前提是指标定义和窗口一致。流量减少不能替代 CPU 归因，默认继续使用 full。未匹配广播也不能直接等同丢包。

## 7. 反证：主动找能推翻结论的条件

每项优化至少问一次：关掉后是否退化？换冷实例是否失效？收尾是否仍正确？观察开销是否改变结果？失败是不是入口/网络/工具引入？回退是否恢复了上一版本？

已取得的反证包括：P2 前两轮被 CPU 保护停止，新读启用后 192/256 人完整通过；delta 与 full 同条件收尾 120 秒失败对 23 秒成功；512 人同额度冷/热的巨大差异；补丁漏内部类后约 15 秒恢复旧包并核对健康与 hash。它们比单纯列一个最大人数更有解释力。

准入 R1/R4 的正确说法是：热实例两轮均完成 96,001 请求、0 最终失败，P50 同为 112 ms；开启保护后 P95 229→261 ms（约 +14%），在途峰值 94→115（约 +22%）。没有重复轮次和误差范围，不能说“完全一致”或“证明没有容量损失”。同样，外网 P50 不能替代持有 semaphore 的服务端平均时间，不能用它套 Little 定律精确算并发额度。

## 能写进简历、也能接受追问的结论

在 2 vCPU、约 1.6 GiB 内存的单实例海南麻将项目中，构建真实对局与战绩混合压测，使用分层指标定位查询、传输、入口和内存瓶颈；通过 P2 读模型在 64 人受控窗口把数据库累计语句耗时降低约 71%，并完成 192/256 人短测与 320 人三轮 15 分钟验证；实现有界缓存、广播编码复用和分层准入保护，保留冷启动、收尾失败及回退证据。

运行边界仍有未闭环部分：delta 间歇性收尾卡死的现场归因与修复、当前准入参数的长稳态和冷启动混合验证、全链路告警送达与恢复验证。256 人两轮 30 分钟已完成，第三轮中止，不写成“三轮全过”；512 人短窗口不能写成长期线上承载承诺。下一轮实验应优先补这些反证，而不是继续堆一个更大人数。
