此实现复用 MySQL、JVM 和现有 JDBC 连接池，不引入 RabbitMQ、CDC 或另一套连接池。仅用于单实例房间关闭后的 Redis 清理补偿，不把出牌、广播或积分结算改成异步任务。尚未部署生产，也未据此提升容量承诺。

## 执行边界

`RoomServiceImpl.stopAndClear` 先将内存房间标记 CLOSED/stop。对于已有数据库场次的房间，通过 Spring 事务代理调用 `RoundPersister.closeWithOutbox`：

1. 沿用 `disbandSession` 的条件更新、会话行锁和提交后战绩缓存失效。
2. 在同一事务插入 `room_close_outbox`。每个 session 唯一，重复事件核对房间码和 generation；不一致则回滚，不覆盖旧任务。
3. 事务提交后同步尝试 Redis `closeRoom`，成功或已被新代际取代，则将事件标记 DONE。确认写入失败时仍保留任务，允许安全重放。
4. Redis 连续失败则仍释放本机房间资源，由持久任务后台补偿。未创建数据库场次的大厅房间保持原同步清理路径。

后台处理只调用已有 Redis Lua 关闭脚本。新一代占用同一房间码时返回 false，旧事件作为已失效任务完成，不删除新代际。Worker 不获取 room/registry 锁，不在 Redis 调用期间持有数据库事务或行锁。重启后从表读取待处理任务，无需内存队列恢复。重放是至少一次语义，不承诺恰好执行一次。

**明确缺口：MySQL 故障导致关闭事务无法提交时，场次结束与事件都会失败。** 当前仍有限重试三次，然后释放本机资源并增加原 `mahjong_room_session_close_failures_total` 告警，需按日志 sessionId/generation 人工核对。这不是持久关闭意图，也没有实现自动扫描历史未结束场次。不要按“超过多久没更新”自动结束真实牌局。

本改动也不能证明历史 `round-drain-timeout` 已修复：该超时可能发生在请求关闭之前。

关闭事务提交前进程崩溃也不在此 outbox 的持久保证内；本实现不是覆盖房间全生命周期的事件日志。

## 资源限制与观测

- 一个名为 `room-close-outbox` 的 daemon 线程，ApplicationReady 后启动，退出时中断；不占用容量采样的调度线程。
- 完成一轮后等待 1 秒，每批最多 16 条；没有常驻任务列表，只读取一批。连接复用现有池，不新增池容量；每次 JDBC 调用结束即归还连接。
- 失败退避从 2 秒递增，最多 300 秒；第 12 次失败转 DEAD，不自动删除或无限重试。异常仅保存类型，避免异常消息泄漏连接信息。
- 每 30 个成功轮询更新 pending/dead/最老等待秒数，并最多删除 100 条一天以前的 DONE。DEAD 保留给人工处理，需监控表增长。
- 索引覆盖 `(status,next_attempt_at,id)` 和 `(status,completed_at,id)`。额外写入、连接竞争和线程内存尚未做生产实测，不能宣称固定增加几 MiB 或 CPU 零开销。

指标：`mahjong_outbox_pending`、`mahjong_outbox_dead`、`mahjong_outbox_oldest_seconds`、`mahjong_outbox_poll_healthy`、`mahjong_outbox_worker_enabled`，以及完成/重试/轮询失败计数。三条新增告警分别覆盖 DEAD、积压超过 120 秒、连续轮询失败。监控配置需单独 reload 才生效。

## 启用、暂停与人工恢复

首次启动由 `RoomCloseOutbox.initialize` 幂等建 InnoDB 表，需 DDL 权限；如果建表失败则明确阻止启动，不静默降级。权限受限环境应先在维护窗口由 DBA 按源码中的 DDL 建表。`CREATE TABLE IF NOT EXISTS` 不校验既有同名表结构，部署前需确认字段和索引。

默认 `ROOM_CLOSE_OUTBOX_WORKER_ENABLED=true`。设 false 并重启仅暂停后台消费，事务内事件仍然写入，同步清理仍继续；不要把它解释为关闭持久化。恢复 true 并重启后继续读取任务。单实例是必要约束，本轮未实现多实例抢占与租约。

人工恢复 DEAD 前，按任务 id 对照 sessionId、room_code、generation、业务状态与错误类型。确认后仅重置指定任务：

```sql
UPDATE room_close_outbox
SET status='PENDING', attempts=0, next_attempt_at=CURRENT_TIMESTAMP(3), last_error=NULL
WHERE id = ? AND status='DEAD';
```

不批量关闭业务场次，不直接删除 Redis key。回退旧 jar 时保留 outbox 表和任务；旧版本不会消费这些任务，需安排补偿处置，不能删表冒充无积压。

## 上线验收（2026-10-17 实测）

- **构建**：92 项测试，0 失败、1 跳过（MySQL 集成测试需专用库，已单独对真库跑通 4/4）；包 `66f6841b49f2ea50`。
- **部署**：`fd-SHA=66f6841b49f2ea50` 确认进程加载的是新包；启动 9 s 健康；`room_close_outbox` 表自动创建；指标 `worker_enabled / poll_healthy / completed / retries / pending / dead / oldest_seconds` 全部可见。
- **8 桌冒烟**：`stopReason=null`；8 条收尾记录全部 `DONE` —— 说明冒烟房间的收尾确实经过 outbox。
- **故障注入（停 Redis → 房间收尾 → 恢复 Redis）**：
  - 停 Redis 后，收尾记录停留 `PENDING`，`attempts 4→5`，`last_error=QueryTimeoutException`；
  - Redis 恢复后，worker 在下一个退避周期自动重试成功：记录转 `DONE`、`completed_total=1`、`pending=0`、`dead=0`，**全程无需人工介入、无数据丢失**；
  - 全链路（含退避）约 2.5 分钟。
- **资源开销**：空闲 `system_cpu_usage` 0.026–0.032（改造前文档基线 0.020–0.059，无可测增量）；`top` 瞬时 CPU 0.0%；额外成本仅一张表 + 每秒一次轮询。
- **告警阈值已修正**：`mahjong_outbox_oldest_seconds` 本就按 `created_at` 计算积压时长 ✓；问题在**阈值**——退避上限为 `min(300, 1<<attempt)` 秒，而告警阈值原为 120 s，**正常退避期间就会误报** ✗。已把 `MahjongOutboxLag` 阈值提到 **600 s** ✓；`MahjongOutboxDead > 0` 保持为"已放弃"的硬信号 ✓。（故障注入时观察到的 `oldest_seconds` 与行 age 有约 15 s 偏差，属抓取时机差异，未再复现，记录待查。）
- **边界**：本机制覆盖"房间收尾（场次关闭 + Redis 清理）"，**不覆盖**对局结算落库；MySQL 无法提交时仍无持久化补偿（与文档开头声明一致）。

### 复现命令

```bash
# 故障注入（服务器上）
bash /tmp/fault-inject.sh stop     # 停 Redis
bash /tmp/fault-inject.sh state    # 看 outbox 行/指标/告警
bash /tmp/fault-inject.sh start    # 恢复 Redis，观察自动补完
```
