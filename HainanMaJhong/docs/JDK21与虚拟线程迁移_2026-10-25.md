## 虚拟线程覆盖范围

- **HTTP / WebSocket 接入任务**：`VirtualThreadConfig` 为嵌入式 Tomcat 显式配置每任务一个虚拟线程的 Executor。Spring Boot 2.7 不识别 Boot 3 的虚拟线程开关，不能只添加配置项。
- **牌局事件**：`RoomEventLoop` 使用 `newThreadPerTaskExecutor(Thread.ofVirtual().factory())`。邮箱和一次性决策完成状态仍有独立锁，同一房间不会并行执行两个事件。保留 `startAsync` / `resumeAsync` 入口，不恢复每房间阻塞循环。
- **推送兜底、Outbox、容量采样**：`VirtualPeriodicTask` 的每次任务使用新虚拟线程，任务完成后才注册下一次延迟，保留 fixed-delay 和不重叠语义。关闭会取消等待任务并中断当前任务。
- **计时基础设施**：保留少量共享平台时钟线程，负责延迟和投递；不在时钟线程中执行数据库、Redis 或 WebSocket I/O。第三方 Netty 的事件循环、JVM GC 和载体线程按其正常机制运行。

虚拟线程不做固定线程池复用。数据源连接池容量和已有准入保护继续限制下游资源，虚拟线程数量不等同于数据库并发额度。

## synchronized 与 pinning 审计

在 JDK 21 上，持有 JVM monitor 时发生阻塞可能 pin 住载体线程。短小纯内存临界区不等于必然有害；需要检查整个调用栈上的外层 monitor，而不仅是最底层网络方法。

此次修改的阻塞路径：

| 路径 | 处理 |
|---|---|
| 房间成员、生命周期、会话创建、结算、关闭、快照与广播 | 各生产调用方统一使用同一个 `Room.lock`（ReentrantLock），保留可重入、互斥和既有业务顺序 |
| 注册表恢复 builder | 注册表复合操作采用 `registryLock`，恢复过程读 MySQL / Redis 时不持有 JVM monitor；保留 room → registry 锁顺序 |
| WebSocket 序号、现场批次与实际发送 | `SessionSendLocks` 返回同一会话的可重入发送锁，序号分配与帧发送仍在同一临界区；弱键避免强引用保留已释放会话 |
| 单局明细缓存 loader | 分条 ReentrantLock，数据库 loader 不在 synchronized 代码块内执行 |
| 战绩聚合查询 | 分条 ReentrantLock，保留同场次聚合/缓存复用语义 |
| 邮箱与决策完成状态 | ReentrantLock，避免框架调用及调度嵌套在应用 monitor 下 |

保留的 monitor 包括真人 pending Map、缓存内存容器、准入桶、发送锁索引及监控内存状态的短临界区；这些区块不包裹数据库、Redis、WebSocket I/O。MySQL 驱动与 Tomcat 也作了版本更新，避免只替换应用外层锁而保留已知第三方监视器问题。

`ThreadMXBean` 和传统 `jvm_threads_*` 指标统计平台线程，不能用它们推断活动虚拟线程总量。新增 `mahjong.virtual.events.active` 和 `mahjong.virtual.events.completed`，分别记录正在处理和累计完成的房间事件。旧引擎线程名称计数仍是旧名称的观测口径，不是虚拟线程总数。

## 回滚到 JDK 17 版本（必须与切包同时进行）

Java 21 构建的 jar **不能用 JDK 17 运行**，反之亦然。回滚是"换 jar + 换运行时"两件事，缺一不可。

```bash
# 1) 确认回滚目标包与运行时都存在
ls -l /root/mahjong/*.jar
ls -d /usr/lib/jvm/* | head

# 2) 切回 JDK 17 构建的包
cp -a /etc/systemd/system/mahjong.service /etc/systemd/system/mahjong.service.bak-rb-$(date +%m%d-%H%M)
sed -i 's#HainanMaJHong-[0-9a-f]*\.jar#HainanMaJHong-<JDK17版本SHA>.jar#' /etc/systemd/system/mahjong.service

# 3) 若 unit 或 drop-in 里写了 JAVA_HOME/PATH 指向 21，一并改回 17
grep -rn 'JAVA_HOME\|jdk-21' /etc/systemd/system/mahjong.service /etc/systemd/system/mahjong.service.d/ 2>/dev/null

systemctl daemon-reload && systemctl restart mahjong

# 4) 三项校验：包指纹、JDK 版本、接口可用
PID=$(systemctl show mahjong -p MainPID --value)
for fd in /proc/$PID/fd/*; do t=$(readlink $fd 2>/dev/null || true); case "$t" in *HainanMaJ*) sha256sum $fd | cut -c1-16; break;; esac; done
grep -E 'JAVA_HOME|java' /proc/$PID/environ -a | tr '\0' '\n' | grep -i java || true
curl -s -o /dev/null -w '%{http_code}\n' -m 5 http://127.0.0.1:9091/actuator/health
curl -s -o /dev/null -w '%{http_code}\n' -m 8 http://127.0.0.1:9091/actuator/prometheus
```

**回滚判据**（任一条即回滚，不观望）：错误率 > 0、P95 明显劣化、启动失败、`/actuator/prometheus` 不可用、对局结算不一致。

## 验证结果

使用实际 JDK 21 执行 `mvn clean package`：**112 项测试，111 通过，0 失败，0 错误，1 项 Redis 实库测试按环境跳过**。

- 400 把固定种子事件摘要与改造前 JDK 17 阻塞引擎基准保持一致；原有机器人、人机应答、迟到应答、取消、抢杠、响应优先级、生命周期和 Outbox 回归均通过。
- 实际启动 Tomcat，通过本机 HTTP 请求确认处理线程 `Thread.currentThread().isVirtual()` 为 true。
- 200 个等待房间验证不保留每房间平台线程，决策回调运行于虚拟线程，取消能及时清理。
- 虚拟线程邮箱在阻塞期间仍保持同房间串行；40 个并发虚拟发送任务的帧序号连续且没有并行写入；周期 I/O 任务为虚拟线程、没有重叠、关闭后不再启动下一次任务。
- 本机使用最大 8 MiB 的 JFR 记录，阈值 5 ms，检查持有房间锁时的实际 Socket 阻塞读取、会话发送和明细缓存 loader 的阻塞路径，未记录到归因于这些应用测试路径的 `jdk.VirtualThreadPinned` 事件。
- 独立正例故意在 synchronized 中阻塞，确认同一 JDK 21 的 JFR 检测器能记录 pinning，避免把检测器无效误判为没有 pinning。
- 发布 jar 已核对新增配置/任务类、Java 21 major 65、Tomcat 9.0.123 和 MySQL Connector/J 9.7.0；校验及测试摘要保存在 `target/virtual-thread-verification.json`。

以上为本机测试结果，不代表生产负载全调用栈绝无 pinning。真实 MySQL / Redis 网络故障和长时高负载尚未针对本版本验证，不能将旧版本的 512 人压测结果直接当作本版本容量验收。本次 JFR 只运行在本机测试进程，没有在生产服务器启用录制。
