1. 正文"384 人是目前已验证的最高短测档位"需补一句：**`ladder-384-96tables` 的 300 秒通过是临界通过**（CPU 峰值 0.92、3 个 >0.9 采样但不连续）；拉长到 1200 秒，第 151 秒即被连续三拍咬住。**长时档位必须按"连续三拍"口径判定。**

## 当前结论与容量定位

1. **收益证据最强的是 P2 新读路径。** 相同 192 人、120 GET/s、V2+gzip 负载，从 CPU 保护中止变为跑满 300 秒；预热失败轮最慢接口 P95 684.4 → 32.6 ms，下降约 **95.2%**；Hikari 排队峰值 51 → 0。64 人受控实验数据库累计语句时间 14.3 → 4.1 s，下降约 **71.3%**。
2. **带宽升级后，新的主要压力落在 CPU，内存余量也很薄。** 384 人短测通过，448 人在 178.2 秒触发 CPU 保护并有 180 次请求失败；448 人应用层估算出流量约 6.57 Mbps。尚无内存保护触发证据，不能直接宣称内存已导致失败，也不能仅凭 CPU 高就认定连接重置的具体原因。
3. **384 人是目前已验证的最高 5 分钟档位，不是长期安全运营上限。** 256 人已有两轮独立 30 分钟通过，是持续运行证据最充分的档位，但第三轮未完成，仍未满足 3×30 分钟交付要求。
4. CPU 无法升级时，优先做：**广播复用序列化 → 定时器线程复用 → 根据剖析结果降低快照/监控/查询成本 → 战绩请求削峰与新房准入保护**。不能承诺这些措施必然让 448/512 人通过。

建议暂以 **256 名混合活跃玩家 / 64 桌**作为运营规划参考，配合资源监控和新房准入；320 人可作为下一轮长期验收目标；384 人保留为短测边界。此建议尚未写入程序，而且 256 人长测可用内存最低仅 185 MiB，仍须监测持续下降。

这里的人数指四人快速真实对局，同时每桌 2.5 GET/s 的混合负载。闲置在线、纯对局、真实用户较低频查看战绩的容量均未单独测出，不能互相换算。

| 档位 | 负载期 CPU 均值 / 峰值 | Hikari 活动 / 排队峰值 | 可用内存最低 | 广播 P95 | 判断 |

| 384 人 | 69% / 92% | 7 / 0 | 143 MiB | 34.4 ms | 尖峰贴近保护线，尚无长期稳定证据 |
| 448 人 | 74% / 95% | 10 / 1 | 126 MiB | 55.6 ms | CPU 保护触发且有连接重置；继续加档没有依据 |

448 人的 6.57 Mbps 来自 `serverApplicationBitsPerSecond`，是 HTTP 与游戏帧的应用层估算，**不是网卡或云端带宽计数**，不能直接把 6.57/20=32.8% 写成精确公网带宽利用率。需要保留网卡、重传、Nginx 和云端限速证据；现有数据更支持优先排查 CPU，而不是继续购买带宽。

384 → 448 人负载只增加约 16.7%，HTTP P95 却增长约 123.3%，广播 P95 增长约 61.5%，说明边缘档位的延迟恶化明显。现有采样无法证明唯一热点，也无法把 ECONNRESET 确定归因于 CPU、Nginx、应用重启或发压链路中的某一处。

可用内存低于告警规则 256 MiB 已在多档出现，但高于压测硬保护线 100 MiB。它是容量风险信号，**没有足够证据判定内存泄漏**：可能包含 JVM 已提交内存、线程栈、MySQL/Redis 增长等，需要长期趋势、进程 RSS 与堆外数据才能区分。

## CPU 无法升级时的后续优化顺序

### 第一批：固定条件，取得热点与故障证据

在 256 人已知通过档位和 320 人候选档位采集短时 CPU/分配/锁等待剖析，结合已有 CPU、GC、线程、Hikari 和快照指标。记录 JAR 哈希、P2 实际开关及门闩、20 Mbps 配置、预热方式、数据规模、账号集合和思考时间。

同时对齐失败时间线：客户端失败样本、Nginx 状态与 upstream 耗时、应用异常、systemd 重启/OOM 记录、TCP 重传/重置。原始失败样本只在本地处理，不将账号和令牌写入报告。**448 人的重置原因是必须补齐的证据项。**

线上出网告警是否已加载 15 Mbps 必须只读核实；当前仓库值正确，文档没有 reload 完成证据。CPU 图表同时展示瞬时 gauge 与 2 分钟 ticks 均值，注明保护每 5 秒采样、指标约 10 秒更新。不要通过放宽保护阈值宣称容量提升。

### 第二批：优先减少可见的重复工作

| 顺序 | 代码证据与改进 | 为什么适合当前约束 | 必须验证 |
|---|---|---|---|
| 1 | `GamePushServiceImpl.broadcastGame` 对每个真人调用 `sendJson`，后者每次 `writeValueAsString` 和 UTF-8 编码计数。普通公共广播先生成含监控序号的最终消息，再序列化一次，四连接复用不可变文本；相同 room_info 同理 | 直接减少四人公共广播的重复序列化和临时分配；该路径序列化次数可从 4 降到 1，**不是全机 CPU 节省 75%** | 保持每连接发送互斥、监控计数、序号与消息顺序；暗杠 owner/full 与其他人 masked 必须分别编码，私人手牌不能复用公共内容 |
| 2 | `RoomManager.start` 与 `resume` 每次创建单线程定时池，结束时 `PromptSupport.shutdown` 关闭。评估应用级有界共享定时器，房间只取消自己任务 | 降低每局线程创建、销毁和栈开销；448 人 JVM 线程峰值 348，具有优化价值 | 超时与真实应答竞态、关闭唤醒、跨房间隔离、任务取消和队列增长；不能让某房间调用 shutdownNow 关闭公共池，也不能在定时线程执行阻塞对局 |
| 3 | `CapacityMetrics.time/bytes/count` 高频创建 builder/查注册表，delivery/acknowledge 使用同一监控对象锁。若剖析证实占比高，预注册有限标签指标并缩小同步范围 | 在保留定位能力的同时降低观测开销 | 标签规模仍有界；四人确认不漏不重，pending 与 expired 一致；保留保护及验收需要的指标 |
| 4 | `RoomSnapshotServiceImpl.save` 在 room 锁内复制与序列化快照；外层调用是否仍持有 room 锁需一并核对。若快照占比高，先减少重复构建，再评估脱离可变房间对象的不可变快照、锁外编码 | 减少锁持有与分配成本，可能改善游戏响应尾部 | 必须保存一致状态，保留 generation/version 原子保护；若合并写入，要明确恢复点目标。不能随意少存快照或将所有保存异步化 |

前两项有明确重复工作证据，但尚无线上热点占比；后两项以剖析结果决定是否实施。共享定时器改造不应顺带把阻塞式房间引擎塞进很小的公共线程池：`PromptSupport` 会等待玩家应答，可能造成其他房间饥饿。

### 第三批：限制战绩与连接突发，保护持续对局

- **确保所有主要客户端走 V2+P2，统计旧接口实际请求量。** `RecordsServiceImpl.selectRecordsList` 仍使用旧 Mapper；P2 实验已看到兼容接口残留 JSON 扫描。若旧客户端仍占较大比例，再将兼容列表内部复用 P2 索引读取并保持旧响应格式；不能凭本轮 V2 扫描归零认定全站扫描已消失。
- **降低无效刷新与重试同步突发。** 现有前端已实现合并、隐藏暂停和退避，先检查线上实际启用与请求分布，再考虑重试抖动、同账号请求并发合并以及战绩请求速率限制。压测的每桌 2.5 GET/s 是对照模型，不应当作真实用户测得频率。
- **新增房间/登录削峰，先保护已在玩的房间。** 用活动桌数、持续 CPU、内存及排队信号决定新房准入；限流响应采用明确业务提示，不无限排队或自动踢掉在局玩家。具体门槛需长测验证，不能只凭 384 人通过设置 96 桌长期上限。
- **不要先扩大 Hikari、Tomcat 线程或 JVM 堆。** 448 人连接池只有短暂排队峰值 1，计算和内存更紧；扩大并发可能增加竞争。先用取得连接耗时、事务占用与剖析决定；内存分配必须同时考虑 MySQL、Redis、堆外与线程。
- **缓存扩容只在真实命中率和内存成本证明有效时进行。** 详情缓存本轮未覆盖；不要因 entries=0 判无效，也不要直接加大缓存。带版本的公共数值/详情可以复用，鉴权仍在读取前完成，昵称变化与玩家私有字段必须正确处理。

如之后能够增加内存而 CPU 仍固定，可单独评估内存升级对余量的帮助；它不会自动解决计算饱和。当前执行计划不以硬件变更为前提。

## 复测与验收安排

1. **先补 256 人第三次完整 30 分钟。** 每轮新目录，维持 160 GET/s 和原保护策略，包含结算、四家分数、战绩、解散和 pending 校验。中止轮保留，不能拼接成完整轮。
2. **为每项代码优化做同条件开/关或前/后对照。** 相同账号与历史快照、预热流程、带宽、负载、接口组合；单项完成后至少先在 256 人比较，再在 320 人验证。记录 CPU 均值与尖峰、分配/GC、线程、内存、连接池、P95/P99、广播与失败。多个改动一起上线只能报告组合收益。
3. **将 320 人作为下一长期目标：3 次独立 30 分钟。** 然后补 384 人长期测试。只有资源趋势稳定且业务校验完整，才考虑 400 → 416 → 432 → 448 人小步短测；遇首个失败停止。512 人保持待测。
4. **补业务覆盖。** 使用隔离的 10/100/1000 局历史，持续单局详情与实际前端刷新场景；覆盖浏览器渲染、慢连接与重连。构造历史不得混入真实用户战绩。
5. **完成较低档位的持续长测。** 先在 256 人或已验证的保守档位观察长时间运行的内存/RSS、GC、Redis、数据库、线程与清理趋势，再做 8 小时验证。没有长期趋势证据前不宣称不存在泄漏。

复测继续采用现有 P2 验收口径和完整窗口要求；旧 10-11 基线允许 P95 <3 秒，后续 P2 要求更严，因此“通过”标签不是同一质量标准。资源保护不是性能目标，内存高于 100 MiB、CPU 未连续超过 90% 也不等于具有运营余量。

## 对原复测文档的口径修正

原文是持续追加的时间线：开头与“环境核对”描述预 P2；“本次容量结论仍然只覆盖什么”描述当时 256 账号上限；后面才追加 P2 开启、长测及 512 账号。上述早期描述应按当时状态理解，不能当成 10-14 最新状态。

原文“上限在 384 与 448 人之间”应表述为：**在该负载、历史规模、预热方式、网络与保护策略下，384 人短测通过，448 人失败，精确边界和长期边界未测。** 原文“384 人当作当前可用上限来运营”缺少长期验收和资源余量依据，本报告不采用为运营承诺。

原文“绑定 CPU 与内存”需要区分：CPU 已触发保护；内存持续减少但未触发硬保护，属于接近边界的风险。未取得 OOM/进程 RSS/堆外证据前，不能将连接重置归因于内存。
