# 运行边界与线上额度定稿

本次冻结已放大额度，削峰优先控制速率；并发许可保留余量，作为保护业务执行资源的最后一道界限。根据已有线上报告与用户确认同步仓库默认值；本次未连接线上、未修改生产环境变量或重启服务。

## 单进程准入预算

| 分组 | 并发上限 | 全局 RPS / burst | 账号 RPS / burst | IP RPS / burst |
|---|---:|---:|---:|---:|
| 登录 | 1 | 3 / 3 | 0.1 / 3 | 1 / 10 |
| 战绩 | 48 | 800 / 100 | 8 / 16 | **480 / 60** |
| legacy 战绩附加限制 | 8 | 20 / 4 | 0.5 / 2 | **12 / 3** |

**IP 层必须低于同组全局**：四层是串联 AND，若 IP ≥ 全局，IP 层在单来源场景永远不会先拒（等于未配置），且单个来源可以吃光整份全局额度。2026-10-16 夜把战绩 IP 由 1200/200 下调为 **480/60**、legacy 由 40/8 下调为 **12/3**（均为全局的 60%）。取值依据：① 低于全局；② 不低到让压测工具自己先被拒（工具单 IP 400 GET/s < 480）；③ 同 IP 约 60 个玩家同时用满每人额度才会触到，对宿舍/校园 NAT 留余量。**线上 `.env` 需改值并重启才生效。**

legacy 同时消耗共享战绩预算。配置入口为 `.env.example`、`application.yml`、`TrafficProtectionProperties`，三处已对齐；实际环境变量优先，修改后需重启应用。令牌桶允许 burst，不能把 800 RPS 视作已验证可持续吞吐。

证据：60 并发登录返回 1 个 200、59 个 429；320 账号按 1.1 秒节拍登录全部成功。热实例 512 人、300 秒、放大额度完成 96,001 请求且 0 最终失败；原始整体验收受未匹配广播门槛限制。冷实例同额度仍出现明显排队，不能承诺冷启动承接同等突发。详见[准入验证](准入保护验证_2026-10-15.md)及[方法论中的更正](八天并发优化方法论_2026-10-16.md)。

并发额度 48 是保留实测配置，并非由公网 P50 推导出的精确最优值；不要继续为降低 CPU 峰值盲目缩到 8。应通过 RPS/burst、准备阶段节拍和客户端有限退避削峰，同时观察拒绝率、延迟与在途。速率拒绝同样可能引起重试反馈，需要共同预算。

## CPU 与内存保护

- 普通压测默认 `GUARD_CPU=0.95`、`GUARD_CPU_SECONDS=60`、`GUARD_MEM_MB=100`。
- 极限监控 CPU 默认同为 0.95 / 60 秒；保留原实验内存底线 `EX_MEM_MB=80`，它是显式极限入口，不是普通运行额度。
- CPU 条件为严格大于阈值、持续有效观测至少 60 秒；以单调时钟计时。首次超阈值后等满时长，下次采样才触发，不用“12 个采样”冒充精确 60 秒。采样失败或超过 15 秒观测间隔重置 CPU 连续窗口；三次抓取失败、主机指标过期仍停止。
- `*_CPU_SAMPLES` 仅兼容旧脚本，映射为 samples×5 秒；显式 `*_CPU_SECONDS` 优先。每轮输出 `guard-policy.json` 保存实际策略，旧轮仍保留旧策略。

发压监控写入停止文件，由发压器停止新负载并收尾；它不是生产入口的 CPU 自适应限流。报告中主机另有低内存重启应用护栏和 swap，但本次未在线核验其当前运行状态。CPU 保护值也不是延迟 SLO，单点达到 99% 不自动等于本轮失败。

| 问题 | 现有证据 | 还不能承诺 |
|---|---|---|
| 正常负载稳定吗 | P2 后 192/256 人短测通过；256 人两轮 30 分钟；内存调整后 320 人三轮 15 分钟 | 当前全部改动已完成同等长测；384/512 人长期稳定 |

| 异常能发现、能回退吗 | 指标/资源停止、P2 读门闩、full/delta、准入开关、旧 jar 回退有记录 | 告警送达人、恢复步骤与每个开关都经过当前版本端到端演练 |

## 放量与回退步骤

1. 核对完整构建包 hash、外置配置、数据库迁移与 P2 回填/promote 状态；P2 读开关不能在未准备的数据上盲开。
2. 重启后显式预热 60–120 秒并渐进升流；预热单独留档，不计入正式窗口。冷启动本身另做验收，不能永远用预热隐藏它。
3. 同时看 latency、最终失败、原始拒绝与重试、连接池、内存和结算收尾；保护触发则记录失败，不用同目录重跑覆盖。
4. 准入紧急回退可设 `TRAFFIC_PROTECTION_ENABLED=false` 后重启；这会移除保护，应同时控制流量。P2 新读退回旧路径需配合降流，旧路径曾在 192 人打满池；delta 退到 full 会增加推送负担。
5. 二进制回退使用上一完整 jar 与对应配置备份，核对 hash、健康、实际查询与对局；不再手工注入几个 class。数据库迁移与应用回退是否兼容另核对，不能自动回滚数据。

delta 256 人修复后通过，但 320 人仍间歇性收尾卡死，且重复轮次无可分辨 CPU 收益；保留默认 full。下一轮优先对间歇缺陷取证、补原始 HTTP 尝试/429 统计、验证冷启动渐进流量与当前额度下的重复长测。本次按要求做文档、配置和构建，不发起线上压测。
