## 三、三条结论

### 3.1 之前"384/400 失败"是**保护策略造成的假失败**

- 保护闸判据是 `system_cpu_usage > 0.9` **连续 3 个 5 秒采样**（15 秒）即强停；
- 而 400 档 CPU **均值只有 0.706**，仅在 **6/74** 个采样短暂到 0.96，**全部验收判据满足**（P95 90 ms、P99 175 ms、广播 P95 40 ms、零失败）；
- 384 档同理（均值 0.687、4/74 超 0.9、全部判据满足）。
- **结论**：在压力画像下，**400 人档本身是健康的**；把 0.9×15 秒当"不可逾越"的红线，会把仍在验收标准内的运行掐掉。建议把强停阈值改为 **0.95 连续 60 秒**（或 0.98×30 秒），内存保护保持不变；也可把强停降级为"记录并继续"。

### 3.2 应用侧的极限在 **448 人**（CPU 首次真正吃紧）

- 448 档：**CPU 峰值 0.98、44/75 个采样 >0.9**（此前 400 档只有 6/74），P95 134 ms、P99 204 ms，并首次出现 73 个失败（含 HTTP 500 与 `ECONNRESET`）。
- 内存仍有余量（467 MiB），**瓶颈是 2 vCPU 的 CPU 本身**。

### 3.3 480/512 的失败**不是应用**，是 nginx 默认连接数撞顶（日志原文证据）

```
[alert] 924#924: *2225780 768 worker_connections are not enough while connecting to upstream
        request: "GET /game?code=595346&seat=EAST&token=...&push=full HTTP/1.1"
```

- `/etc/nginx/nginx.conf`：**`worker_connections 768`**（`worker_processes auto` = 2 个 worker），且 worker 的 **`Max open files` 软限制仅 1024**；
- 每条 WS 在 nginx 占 **2 个连接槽**（客户端 + upstream），480 条 WS ≈ 960 槽，再叠加 250 rps 轮询的 keepalive 连接 ≈ 400 槽 → 逼近单 worker 的 768 上限 → 新连接（含 WS 握手）被拒 → 客户端看到 **500**；
- 同时段 nginx error.log 共 **42 条** `worker_connections are not enough`，**0 条** `connection refused` / `too many open files`；应用侧**零异常**（仅清理期 400）、HikariCP **零超时**（max=10、pending=0）、进程 fd 仅 27 个；
- **480/512 时应用 CPU 只有 0.27–0.31** —— 连接根本没进来。

## 四、修复建议（需确认；此前指示为"暂不扩大连接池/带宽"）

1. **nginx**：`worker_connections 768 → 4096`（或 8192）、新增 `worker_rlimit_nofile 65535;`、并把 nginx 的 systemd `LimitNOFILE` 软限制从 1024 提到 65535；
2. **nginx upstream 启用 keepalive**（`upstream mahjong { server 127.0.0.1:8080; keepalive 64; }` + `proxy_http_version 1.1; proxy_set_header Connection "";`）以减少 upstream 连接槽占用；
3. 复测 **480 / 512**，再确认应用侧 CPU 与 P95 在哪一档真正崩（预计 480–512 之间）。

> 注意：**账号只有 512 个、工具上限 128 桌 = 512 人**，要测更高档位需先补齐账号并提高工具上限。

### 4.4 修复后的结论（替换第三节的 3.3）

1. **nginx 默认配置确实是此前 480/512 失败的唯一原因**：修复后 480 人**零失败通过**、512 人跑完全程且**零 HTTP 失败**。
2. **应用侧的极限现在落在 512 附近**：512 档 CPU **峰值 0.99、122 个采样里 57 个 >0.9**（≈47%），而 CPU 均值仅 0.59 —— 说明瓶颈是**短时峰值把 2 vCPU 打满**，延迟随之抬升（P95 90→229 ms、广播 P95 40→91 ms）但**仍在验收画像内**。
3. **内存不是约束**（512 档仍有 482 MiB）。
4. **测量上限已到工具的边界**：账号 512 个、工具 `tables ≤ 128`（=512 人）。要继续往上必须补账号并放宽工具上限。
5. 若要进一步提升容量，方向是**压 CPU 峰值**（短时并发的 CPU 尖峰）与**读接口缓存**，而不是加带宽或加连接池。
