# 320 人负载下的热点归属（第 1 步，2026-10-15）

目的：按《逐项优化与线上容量对比_2026-10-14》第一批要求，先取得"CPU 花在哪"的证据，避免盲改。
方法：**不使用 JFR**（10-15 事故后禁用 profile 级录制），改用三种低开销手段组合：
1. `/proc/<pid>/task/*/stat` 增量 → **按线程组聚合的 CPU 份额**（纯 bash 读取，无采样钩子）；
2. `jstack` 反复采样 → RUNNABLE 线程栈分类（业务功能归属）；
3. 应用自带 Micrometer 指标 + 压测工具的分位数据。

环境：ECS 2 vCPU / 1608 MiB，**已加 4 GB swap**（swappiness=20），已装主机侧内存护栏（连续 90 秒低于 80 MiB 重启应用）。
时段：2026-10-15 12:33–13:27（应用 12:25 硬重置后冷启动，前两轮含冷 JIT 影响）。

## 四、方法学发现（对后续所有 A/B 都重要）

1. **冷 JIT 是重启后的最大单点消耗**：256 人轮开局，`C2 CompilerThre` 单线程吃到 **47–49% 的一个核**（持续约 20 秒），之后回落到 2–11%。这解释了为什么**每次重启后的第一个大档位**总在登录阶段撞 CPU 保护（2 vCPU 上，编译与业务抢核），而热机时同档位轻松通过。→ **A/B 必须先预热**（本系列统一用 16 桌 60 秒预热后再测）。
2. **采样器本身会改变被测对象**：同一档位、无采样时 P95 45.8 ms；纯 /proc 分组采样 62.8–97.6 ms；**`jstack` 每 5 秒则达 140.8 ms**（safepoint 代价）。→ 优先纯 `/proc` 采样；`jstack` 只在必须定位锁/栈时用，且降低频率。
3. `room-bind-<房间码>` 每房一条裸线程这件事，文档与既往优化清单里都没有出现；它与《逐项优化》里"共享定时器（`mahjong-timer`）"是**两个不同的每房线程问题**，前者是引擎执行线程，后者是等待玩家应答的定时池。

## 五、可立即行动的结论（不需要更深的剖析也有依据）

1. **监控开销不是主因**（1.6%），**数据库也不是**（2.4%）——不必优先动这两块。
2. **输出量是主要消耗**（socket 写占栈顶近一半）：广播复用序列化（第 2 步）方向正确，且应同时关注"每人一份响应"的整体字节量。
3. **每房一条裸线程**（`room-bind-*` 80 条 + `mahjong-timer` 80 个单线程池）值得评估：裸线程本身不贵（每条约 0.25% 一个核），但 80 个线程 + 80 个 `ScheduledThreadPool` 的创建/销毁与上下文成本在更高档位会放大。
4. **房间引擎只占 25%**：即使把引擎优化到 0，也只能省下约 0.2 个核；**HTTP/WS 路径（65%）才是主战场**。

## 六、仍未回答的问题与建议路径

"Tomcat 那 65% 里，广播序列化 / 快照 / 监控 / 记录查询各占多少"——**本轮工具答不了**（4 帧栈采样太浅，且 RUNNABLE≠on-CPU）。三条路：

1. **async-profiler（推荐）**：单个 jar、attach 模式、`-e cpu -d 60`，开销 1–2%、无内存仓库风险。需操作者批准在线上放置该 jar。
2. **JFR `settings=default`**：比事故那次的 `profile` 温和得多，且必须加 `-XX:FlightRecorderOptions=repositorysize=32m,disk=true` 绑定内存；仅 256 档跑 60 秒。仍需操作者确认。
3. **定向计数（无需新工具）**：在 `GamePushServiceImpl.broadcastGame`/`sendJson` 上加计数器，直接测"一条公共广播序列化几次、平均耗时多少"——这正好是第 2 步要改的代码，可把测量与改造合并。

在操作者选定之前，不建议直接开始第 2 步的代码改动。
