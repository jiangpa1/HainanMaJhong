# 并发模式与失效清单

2026-10-16 按当前源码盘点。“已实现”仅代表存在实现；验证状态以实测报告为准。以下路径均相对 `src/main/java/hainanMahjong/`，前端与工具路径另标。

| 模式 | 实现入口 | 什么时候会出事 | 怎么防；还要注意什么 |
|---|---|---|---|
| 房间内串行修改 | `room/Room.java`、`service/impl/MultiPlayerRoomServiceImpl.java` | 入退房、动作、重连同时改成员与阶段 | 同一房间锁保护状态与阶段；跨房共享索引另协调。锁内慢 I/O 仍可能拖长等待 |
| 多索引原子协调 | `room/RoomRegistry.java` | 用户归属和房间成员分开更新，产生双重归属或孤儿记录 | 注册表同步协调复合操作；ConcurrentHashMap 不能代替业务事务 |
| 终态、代际与版本防迟到写 | `repository/RoomSnapshotRepository.java`、房间生命周期服务 | 解散后旧异步任务覆盖 Redis，新房复用编号遭旧任务污染 | CLOSED 终态、generation/version、Redis Lua 条件更新；迟到任务失效，取消定时任务。生命周期竞态有专项验证 |
| 事务、唯一约束与幂等结算 | `service/impl/RoundPersister.java` | 结算重入、重试、并发写分数，产生重复账或半份投影 | 行锁、事务、唯一键协调；四家结果与 P2 投影同事务，提交后失效缓存。不能把“HTTP 成功”代替账目核对 |
| 缓存击穿合并 | `service/impl/RecordDetailCache.java` | 同一冷 key 瞬间涌入，所有线程同时查库 | 分段锁控制加载；不同 key 仍可并发。冷启动多 key 不会因同 key 合并自动解决 |
| 有界缓存、TTL 与版本键 | 同上；P2 查询服务 | 缓存无限增长、旧局详情命中新内容、过期同时回源 | 条目/字节上限、TTL 与随机扰动、版本化 key；监测命中与加载。不把缓存当持久层 |
| 前端 single-flight | `frontend/src` 战绩 store 与认证请求层；`docs/performance/online-capacity-retest.mjs` | 页面组件重复查询；token 同时过期造成刷新风暴 | 合并相同在途读取和 token 刷新；失败后释放占位。写操作不能按读请求方式盲重试 |
| 首响应胜出与超时撤销 | `engine/PromptSupport.java` | 多个响应竞争、超时与响应同到；取消任务仍留队列 | 原子完成/锁存协调，超时与业务结果只提交一次；取消任务可移除，局结束清理。每局 scheduler 仍有资源成本 |
| 单连接发送互斥 | `service/impl/GamePushServiceImpl.java` | 多线程写同一个 WebSocket，帧交错或发送异常 | session 级同步，发送失败关闭/清理；慢连接仍会拖住发送方，当前没有完整异步有界发送队列 |
| 不可变编码共享与权限隔离 | 同上 | 给四家重复序列化；复用私有手牌给其它玩家 | 公共载荷复用，完整/遮蔽载荷分开；共享对象不可变，统计编码数与发送数。曾漏打包内部类，改走完整构建 |
| 事件合并 + 时间兜底 + 生命周期屏障 | `service/impl/GameEngineServiceImpl.java` | 最后一批事件依赖下一次动作刷新，房间静默后永久挂起 | 50 ms 定时检查、捕获不可变状态、结算/阶段边界刷新；线程调度延迟意味着不是硬实时 50 ms。Phase 1 修复后仍需完整复验 |
| seq、快照与 resync | `GamePushServiceImpl`、`MultiPlayerRoomServiceImpl`、前端协议处理 | 增量状态缺口、重连后拿旧状态；客户端反复 resync | 连接级 seq、重连重建基线、周期/强制快照、resync 节流。seq 检测缺口不等于自动可靠投递，工具未匹配也不直接证明丢帧 |
| Semaphore 准入闸门 | `service/RequestAdmissionGuard.java` | 密码校验/查询同时涌入，挤满 Tomcat、DB 或 CPU | `tryAcquire` 立即拒绝，许可幂等关闭、异常路径释放；不给服务端新增等待队列。额度过小也会制造拒绝与重试积压 |
| 多维令牌桶 | 同上；`config/TrafficProtectionProperties.java` | 单账号刷接口、集中登录、NAT 用户共用 IP；key 被恶意打散 | 全局/账号/IP 独立预算，legacy 额外约束；key 数与空闲 TTL 有界，容量不足也明确拒绝。单进程额度不等于多实例全局额度 |
| 可信代理边界 | 准入取 IP 逻辑与 Web 配置 | 攻击者伪造 X-Forwarded-For 绕过 IP 桶 | 只信任实际 TCP peer 白名单，从可信链解析客户端；代理拓扑变更同步配置，不能无条件取首个头 |
| 429 + Retry-After + 分类指标 | `exception/GlobalExceptionHandler.java`、`monitoring/CapacityHttpFilter.java` | 保护拒绝被当 500；客户端立刻重试；监控把主动拒绝藏掉 | 明确 429、Retry-After，区分 concurrency/global/principal/ip/key_capacity，单列 rate_limited 与 inflight |
| 有限退避与随机抖动 | `frontend/src/api/api.js`、`composables/useRecordTask.js`；压测工具 `request()` | 所有客户端同秒重试形成周期尖峰；重试无限叠加 | 战绩读取最多重试四次，遵守 Retry-After 和退避；前端与工具抖动窗口不同（工具 0–200 ms）。登录和行动不自动重放。需分别统计尝试和逻辑请求，重试预算不能代替限速 |
| 资源护栏与失败可见 | `docs/performance/monitor*.mjs`、`cpu-guard.mjs`；监控规则 | 瞬时 CPU 尖峰误停；采样故障被当健康 | CPU >0.95 持续观测至少 60 s；内存底线、采样失败/过期停止，记录策略；断样重置持续计时。发压护栏停止压测，不会自动给线上用户限流 |

## 三种必须区分的“并发”

客户端在途数包含网络、等待与重试；Tomcat 工作线程是请求执行资源；业务 semaphore 只覆盖其保护代码段。三者不能直接互换。Little 定律只在相同系统边界、稳态和平均量下使用，应采集服务端许可持有时间后估算，再给尾延迟留余量。

## 关键实测与剩余验证

- 60 并发登录：1 成功、59 个 429；200 次同用户查询：8 成功、192 个 429，主要命中用户速率桶，不能当作纯并发闸门实验。
- 512 人热实例、放大额度：96,001 成功、0 最终失败；冷实例同额度仍有 P95 12.2 秒与 2,035 在途。准入不能替代预热、渐进放量和连接排队治理。
- delta 原轮 64/64 房间收尾失败；补救后 256 人通过，320 人仍间歇复现。默认 full，不能写成全量修复。
- 房间线程与每局定时器仍有规模成本；慢 WS 缺完整发送队列隔离；多实例需要共享额度、所有权与跨节点协调。它们是后续方向，不描述为当前已实现。
